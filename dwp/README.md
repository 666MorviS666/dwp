# dwp — вероятность победы в Dota 2

Две модели: оценка по драфту до старта и оценка по состоянию на поле
поминутно, плюс разложение каждой оценки на вклады и детектор переломных
моментов.

Целевое применение — аналитика и оверлей для трансляции.
**Не для ставок.** Почему — в разделе «Почему это не годится для ставок».
Это не оговорка для галочки: там перечислены конкретные механизмы, из-за
которых калиброванная модель всё равно проигрывает рынку.

---

## Быстрый старт

```bash
pip install numpy pandas scikit-learn lightgbm requests

python -m dwp.synthetic        # ~3 с: 4000 матчей с известной истинной силой
python -m dwp.train            # ~10 с: обе модели, калибровка, метрики
python -m dwp.analyze --random 3
python -m dwp.check_schema --source synthetic
```

С чистой машины `synthetic` + `train` — **14.1 с** (Python 3.12, 1 CPU).

Реальные данные:

```bash
python -m dwp.collect --n 2000        # возобновляемо, можно прерывать
python -m dwp.check_schema            # ОБЯЗАТЕЛЬНО до обучения, см. ниже
python -m dwp.train --source real
```

Лайв — проще всего через браузер, одной командой:

```bash
export STEAM_API_KEY=...
python -m dwp.web              # http://127.0.0.1:8765/
```

Там три раздела: **матчи** (список идущих игр, выбор кликом), **данные и
обучение** (скачать матчи, обучить ансамбль, все замеры — с живым логом) и
**точность** (три главные строки, метрики моделей, калибровка лайва).

Окна панели двигаются мышью, в двух режимах на выбор (кнопка «раскладка»):
в сетке — левый край меняет окна местами, правый задаёт ширину; свободно —
шапка переносит окно в любую точку, маркеры по периметру задают ширину и
высоту. См. «Раскладка».

Набор моделей для боя (ансамбль по сидам, −0.0052 log loss и вдвое лучше ECE
против одиночной — см. «Ансамбль в бою»):

```bash
for s in 3 5 7 11 13; do
  python -m dwp.train --source real --live-features --extra-features \
      --exact-features --gold-norm add --rating player --seed $s \
      --out "models/ens_$(printf %02d $s).pkl"
done
python -m dwp.bench_models                 # все модели на холдауте + кэш
python -m dwp.verdict --tune --frontier    # правило вердикта по этому кэшу
```

Порядок важен: `bench_models` пишет `data/holdout_preds.npz`, из которого
`verdict --tune` подбирает правило. Обучили заново — пересоберите и то и
другое, иначе вердикт останется от прежних моделей.

То же самое одной кнопкой: панель → «данные и обучение» → «Переобучить всё
заново» (`retrain_all` в `dwp/jobs.py` — те же шаги в том же порядке).

То же в консоли:

```bash
python -m dwp.live --list
python -m dwp.live --dump --server-steam-id <id> > raw.json   # сверьте схему!
python -m dwp.train --no-xp                                    # лайв без XP
python -m dwp.live --watch --server-steam-id <id> \
    --model models/live_exact.pkl --log
python -m dwp.livecheck        # калибровка лайва по досмотренным матчам
```

Проверка лайв-пути без сети — на завершённых матчах из `data/matches`:

```bash
python -m dwp.test_live_replay --n 40 --model models/ens_*.pkl
python -m dwp.test_live_fixture
python -m dwp.test_builds
python -m dwp.test_killfeed        # лента: пары не выдумываются
python -m dwp.test_forecast        # коридор молчит там, где данных нет
python -m dwp.test_web_snapshot    # весь веб-путь на настоящем матче
```

Последний — сквозной: берёт завершённый матч из `data/matches`, поминутно
собирает из него ответы в схеме `GetRealtimeStats` и гонит через тот же
`Poller.snapshot`, что работает в браузере. Проверяет заодно, что число на
панели совпадает с числом консольного пути до 1e-9.

Слепой тест — оценка без знания исхода, с запечатыванием (см. раздел ниже):

```bash
python -m dwp.blindtest --seal --n 200
python -m dwp.blindtest --reveal --worst 12
python -m dwp.blindtest --quiz --n 10        # сыграть самому против модели
```

Сборки и шансы отстающих:

```bash
python -m dwp.builds --table                 # ~25 минут на всей выгрузке
python -m dwp.builds --from-file data\live_dump_late.json
python -m dwp.damage --check                 # есть ли урон в лайв-ответе
```

**Инструменты замера.** Их легко не заметить, а половина констант проекта
обоснована именно ими — до аудита 14.08.2026 ни один не был упомянут в
документации, и найти их можно было только просмотром каталога:

```
bench.py               сравнение вариантов на выгрузках, режимы single/multi/ab.
                       `multi` печатает разброс по сидам — то самое число,
                       меньше которого правку принимать нельзя

                       разбиениях. Отсюда взяты config.RELIABILITY_BANDS

                       ошибка модели или честная неопределённость поздней игры

                       Отсюда config.DRAFT_ELO_SCALE = 10 и DRAFT_C = 0.02
check_aegis.py         ЖЁСТКАЯ проверка OLD_ROSHAN_KILL_TEAM_MEANS через
                       player_slot аегиса — сильнее косвенной сверки
check_accounts.py      хватит ли истории на игроках, чтобы Elo по пятёрке был
                       точнее Elo по team_id (п. 3 в «Что доработать»)
export_rosters.py      выгрузка составов под тот же вопрос про Elo игроков
```

Все семь проверены запуском 14.08.2026 и работают.

**Драфт-модель.** Вход: вектор длины `n_heroes` (+1 за героя Radiant,
−1 за героя Dire) плюс пред-матчевая разница Elo, делённая на 400.
Логистическая регрессия `C=0.05` в `CalibratedClassifierCV`.
Коэффициенты интерпретируемы как вклад героя.

**Стейт-модель.** LightGBM по поминутным срезам: минута, разница
нетворса и две её производные, перевес по вышкам и баракам, число
потерянных вышек каждой стороной, Рошаны, минут с последнего Рошана,
и логит драфт-модели отдельным признаком. Изотоническая калибровка на
отдельной выборке.

Схема разбиения — **всё по `match_id`, не по строкам**:

```
все матчи
  ├── test   20%          только финальная оценка
  └── train_pool 80%
        ├── fit   60%     деревья
        ├── val   15%     ранняя остановка
        └── calib 25%     изотоника (её половина — на выбор обрезки хвостов)
```

## Как соблюдены обязательные требования

1. **Сплит по `match_id`.** `GroupShuffleSplit` для теста, валидации и
   калибровки. В `train.py` стоят `assert` на непересечение.
2. **`duration` не признак.** `assert` на список запрещённых признаков —
   проверка стоит копейки, а модель, отличная офлайн и мёртвая в лайве,
   по метрикам не видна.
3. **`draft_prior` out-of-fold.** `cross_val_predict` по `train_pool`.
   Каждая строка драфт-матрицы = один матч, поэтому обычный KFold здесь
   уже является сплитом по `match_id`.
4. **Elo пред-матчевый.** `match_id -> разница` считается хронологически
   и хранится в артефакте. `analyze` берёт оттуда и печатает источник;
   финальный рейтинг используется только для матчей, которых в таблице
   нет, и это тоже печатается.
5. **Метрика — log loss и Brier.** Accuracy печатается, но третьей
   колонкой. Reliability по децилям и разбивка по десятиминутным
   отрезкам — обязательная часть вывода.
6. **`--no-xp`.** XP из уровней не достраивается нигде. `live.py`
   **отказывается** загружать модель, обученную с XP, с объяснением.

## Развилка: калибровка драфт-модели

`CalibratedClassifierCV(method="isotonic")` вредит при малом объёме
данных. Замерено на тесте:

| матчей в обучении | isotonic | sigmoid | без калибровки | база |
|---|---|---|---|---|
| 960 | 0.6975 | 0.6837 | **0.6797** | 0.6947 |
| 3200 | 0.6446 | **0.6405** | 0.6403 | 0.6930 |

На 960 матчах изотоника **хуже базовой линии**: это ступенчатая функция,
и на ~190 точках внутреннего фолда ступени получаются грубыми. AUC при
этом не падает — по accuracy проблему не увидеть.

Про-матчей несколько тысяч в год. Если обучаетесь на одном сезоне, вы
попадаете ровно в проблемную зону.

Умолчание оставлено как в ТЗ (`isotonic`). Есть флаг
`--draft-calib {isotonic,sigmoid,none,auto}`, и сравнение всех трёх на
out-of-fold печатается при каждом запуске — выбор ваш, но он виден.

Та же проблема у стейт-модели решена иначе: изотоника выдаёт ровно `0.0`
и `1.0` на хвостах (3.6% диапазона), один ошибочный ряд там стоит ~14 в
log loss. Хвосты обрезаются, уровень обрезки выбирается на отдельной
половине калибровочной выборки.

## Ловушка: вклады условные, а не маргинальные

`pred_contrib=True` даёт точный разбор деревьев, но вклады условны при
фиксированных остальных признаках. Измерено на тестовой выборке,
минуты 30–40:

| потеряно вышек Radiant | винрейт Radiant | он же при \|gold_adv\| < 3000 |
|---|---|---|
| 1 | 0.83 | 0.25 |
| 5 | 0.36 | 0.60 |
| 9 | 0.18 | 0.74 |

Маргинально зависимость падающая, при контроле золота — **растущая**.
Логика реальная: команда, отдавшая девять вышек и всё равно сравнявшая
золото, сильно отыгралась.

Поэтому строка «Radiant потерял 9 вышек: +0.37» в разложении корректна,
но на экране будет прочитана как ошибка модели. Для комментатора такие
строки надо переформулировать вручную. `analyze` печатает
предупреждение об этом.

## Валидация схемы: что проверяется, а что нет

`check_schema` ничего не додумывает. Каждое допущение либо
подтверждается данными, либо помечается как непроверяемое.

**Проверяется жёстко.** Смысл поля `team` в старом
`CHAT_MESSAGE_TOWER_KILL` — документацией не закреплён. Обе гипотезы
(`team` = кто потерял / кто снёс) сверяются с popcount битовой маски
`tower_status_*` в конце матча. На синтетике сверка различает их
уверенно: `victim=1.000` против `killer=0.054`. Если на реальных данных
ни одна гипотеза не сойдётся — модуль выдаёт ПРОВАЛ и просит не обучаться
на этих данных.

**Проверяется косвенно.** Смысл `team` в `CHAT_MESSAGE_ROSHAN_KILL` —
сверять не с чем, битовой маски для Рошана нет. Единственное измеримое —
правдоподобие: под верной трактовкой победитель убивает Рошана чаще.
Это не доказательство, и модуль так и пишет.

**Не проверяется вообще.** Схема `GetRealtimeStats`. Она
недокументирована, пути в `live.extract_state` взяты по памяти. Для этого
есть `--dump` и `--explain-fields`: первый печатает сырой ответ, второй —
таблицу «какое поле где нашлось». Сверьте их до того, как доверять
числам. Допущение «`buildings[].type` 0 = вышка, 1 = барак» тоже не
проверено, и `extract_state` печатает наблюдаемое распределение `type`.

**Молчаливого нуля нет нигде.** Не нашлось поле — признак становится
`NaN` (LightGBM обрабатывает пропуски штатно), и об этом печатается
предупреждение. Ноль в признаке по вышкам неотличим от «вышек не
теряли» и стоит одного из сильнейших сигналов, а по метрикам это почти
не видно.

**Это утверждение было неверным, и ровно в том месте, про которое
написано.** Один молчаливый ноль в лайве всё-таки был — по зданиям, и
нашёл его реплей-стенд (`test_live_replay`), а не рассуждение.
`extract_state` клал в `towers_lost[team]` ключ только при наличии
стоящих вышек этой стороны, а `build_row` проверял словарь на непустоту
целиком: `if tow:`. Когда сторона теряет **все** 11 вышек, её ключ
исчезает, словарь остаётся непустым за счёт второй стороны — и в признак
шёл ноль. На живом слепке с мегакрипами у Radiant это давало
`tower_adv = +3` («Radiant впереди по вышкам») у команды без базы, и
оценка **росла**: 32.3% вместо 18.7%. В реплее 40 матчей максимум
расхождения с офлайн-путём был 62.5 п.п., в семи матчах с мегакрипами
последние десять минут расходились в среднем на 28.9 п.п.

Почему это не поймали фикстуры: в `test_live_fixture` во всех сценариях
`tow_r < 11`, то есть ключ всегда на месте. Отсюда и вывод, который
стоит дороже самой правки: **инвариант, проверенный только на фикстурах,
которые вы сами и придумали, не проверен.** Теперь есть
`test_live_replay` — он гоняет настоящие матчи и падает, если в выборке
нет ни одного матча с потерянными всеми 11 вышками.

Исправлено так: длина списка `buildings` в `GetRealtimeStats` постоянна
(снесённое здание остаётся в списке с обнулёнными полями), поэтому при
`len(buildings) == config.N_BUILDINGS_TOTAL` и стоящих тронах обеих
сторон отсутствие ключа означает именно «стоящих ноль». Если хоть одно
из условий не выполнено — `NaN` и `rep.miss`, как и было обещано.
`build_row` требует `len(tow) == 2`.

## Веб-панель: `python -m dwp.web`

Одной командой, без аргументов:

```bash
python -m dwp.web            # -> http://127.0.0.1:8765/
```

Дальше всё в браузере. В шапке три раздела:

```
матчи                список идущих игр, клик по строке — панель матча
данные и обучение    скачать матчи, обучить ансамбль, все замеры
точность             три главные строки, метрики моделей, лайв-калибровка
```

`--server-steam-id` остался, если хочется сразу конкретный матч, а
`--from-file` крутит сохранённый ответ без сети.

### Раздел «данные и обучение»: длинные задачи из браузера

Раньше панель показывала матч, а всё остальное жило в консоли: сбор
данных, обучение, замеры. Держать это в двух разных местах — значит
гарантировать, что половина никогда не запустится. Теперь задачи
запускаются из браузера, с живым логом и кнопкой «прервать»:

```
Скачать матчи                  возобновляемая загрузка с OpenDota
Проверить схему данных         обязательна перед обучением на новых данных
Обучить одну модель            один сид
Обучить ансамбль (5 сидов)     около пяти минут
Замерить ансамбль на холдауте  и записать вскрытие в реестр
Кривая обучения                нужны ли ещё матчи, ~15 минут
Собрать коридор неопределённости
Проверить экстраполяцию темпа
Калибровка лайва               добрать исходы и посчитать ECE
Прогнать все проверки          вся гигиена одной кнопкой
```

**Что тут было важно не сделать — дырку в машине.** Веб-сервер слушает
порт, и принимать от него команды на исполнение нельзя ни в каком виде.
Поэтому (`dwp/jobs.py`):

- команда **не приходит из браузера**. Браузер называет ключ из
  фиксированного списка `SPECS`, а сама командная строка собирается на
  сервере;
- параметры — только числа, и каждое проверяется границами (`--n` от 10 до
  20000, сид от 1 до 999). Строка в оболочку не попадает вообще:
  `subprocess.Popen([sys.executable, "-m", *args])` без `shell`;
- запуск идёт методом **POST**, а не GET: GET браузер может дёрнуть сам —
  предзагрузкой ссылки или восстановлением вкладки, — и обучение стартовало
  бы без ведома человека;
- **одновременно идёт одна задача.** Два обучения на одной машине только
  отнимают друг у друга процессор, а два `collect` дерутся за один файл
  состояния.

### Раздел «точность»

Наверху три строки, ради которых раздел и открывают, — все три с ОДНОГО
вскрытия слепого холдаута, поэтому их можно ставить рядом:

```
лайв-модель, каждую минуту матча    72.7%   log loss 0.5180 · ECE 0.0121
драфт-модель, до начала игры        55.4%   AUC 0.5825
ВЕРДИКТ, одна сторона на матч       75.3%   95% [72.4, 78.0], на 11-й минуте
```

Ниже — метрики артефактов, лайв-калибровка по фактически показанным на
экране числам и реестр вскрытий холдаута. Ни одно из них не «главное»:
офлайн-метрика меряет модель, лайв меряет то, что видел зритель, и они
расходятся — на восьми матчах ECE лайва был 0.126 против обещанных офлайн
0.021–0.034.

Собственные метрики моделей между собой **не сравнимы** и так и подписаны:
у разных сидов разные тестовые выборки.

### Панель матча

Шесть окон, и больше на экране ничего нет:

- **вердикт** — одна сторона на весь матч и доля, с которой такие вердикты
  сбывались (отдельный раздел ниже);
- **табло** — счёт крупно, время, перевес по золоту, вышки, бараки;
- **сборки обеих команд** — предметы по слотам, уровень, общая на обе
  команды полоса нетворса, свободное золото; отдельный раздел ниже;
- **карта** — герои иконками, снесённые здания, линии, река и лес;
- **лента событий портретами** — кто кого убил, какие здания пали;
- **драфт** — у кого сильнее и на сколько, «почему» списком, разбор по
  героям под раскрытием.

Плюс **слепой режим**: число модели закрыто, зритель называет своё, ответ
ложится в `data/blind/live_guesses.csv`; посчитать потом
`python -m dwp.blindtest --guesses`.

Матч **пишется сам** в `data/live_log/<match_id>.csv` тем же
`livelog.LiveLog`, что и консоль; выключается `--no-log`. При смене матча
трекер и лог начинаются заново — окна производных считаются от момента
подключения, и тащить их с прошлого матча значило бы показать выдуманный
темп.

#### Что с панели убрано 16.08.2026 и почему

Убрано не спрятано, а вырезано вместе с кодом: перспектива (коридор, темп,
«что ещё не разыграно»), «что двигает число» (разбор вкладов), «чего модель
не знает», «кто против кого» сеткой 5×5, кривая вероятности, текущий
процент числом, строка Stratz и все подписи-пояснения под блоками.

Причина одна и она же для всех: **на экране должно стоять то, по чему
принимают решение**. Вердикт не меняется — а рядом с ним скакал процент, и
два числа спорили друг с другом. Коридор и вклады объясняли, откуда взялось
число, которого больше нет на экране. Подписи объясняли подписи.

Что уцелело от снятого: коридор по-прежнему считается и печатается
(`python -m dwp.forecast --check`), разбор вкладов — в `dwp.live --once`,
статистика пар Stratz свелась к одной строке в «почему» под драфтом,
а вероятность Stratz продолжает писаться в лайв-лог колонкой `p_stratz`,
чтобы потом сравнить, кто врал больше (`dwp.livecheck`).

#### Раскладка: окна двигаются мышью

Два режима, переключатель — в полосе, которую открывает кнопка «раскладка».

**Сетка** (по умолчанию) — двенадцать колонок:

```
левый край окна        тянуть → поменять местами с тем окном, на которое
                       отпустили (меняются и позиция, и ширина, поэтому
                       сетка не перекладывается — окна просто меняются)
правый край            тянуть → ширина, от 3 до 12 колонок
правый нижний угол     тянуть → масштаб содержимого, от 60% до 200%
```

**Свободно** — у окна появляются собственные координаты, и его можно
поставить куда угодно и сделать каким угодно:

```
шапка окна (верх)      тянуть → перенести в любую точку полотна
восемь маркеров        тянуть → ширина И высота, минимум 220×90
по периметру           (края двигают свой край, углы — оба сразу)
Ctrl + колесо          масштаб содержимого, от 60% до 200%
Alt во время тяги      выключить прилипание
щелчок по окну         поднять над соседями
кнопка «плиткой»       разложить заново по сетке, сохранив высоты
```

Края прилипают к краям соседних окон, к краям полотна и к его середине
(порог 7 px); прилипание показано направляющей. Полотно в этом режиме
занимает всю ширину окна браузера, а не 1360 px: «поставить куда угодно» и
жёсткий потолок ширины плохо сочетаются.

Ручки и маркеры видны при наведении на окно; кнопка «раскладка» делает их
видимыми постоянно. Всё лежит в `localStorage` под ключом `dwp.layout.v2`
(старый `v1` читается как сетка без свободной части) и переживает
перезагрузку.

Четыре вещи, которые здесь важны технически.

**Масштаб сделан через `zoom`, а не через `transform: scale`** — второй
рисует увеличенное окно поверх соседей, не меняя его места в сетке, то есть
увеличенные сборки залезли бы на карту. `zoom` меняет размер самой коробки,
и сетка раздвигается.

**В свободном режиме у окна три уровня разметки, и каждый нужен.** Коробка
держит маркеры и не прокручивается, `.cbody` прокручивает содержимое,
`.czoom` его масштабирует. Свести прокрутку и `zoom` в один элемент нельзя:
`zoom` умножает и `inset`, и окно поехало бы вслед за масштабом.

**Полотно образует свой контекст наложения** (`isolation: isolate`). Без
него `z-index` окон конкурирует с липкой шапкой, у которой 5, — и поднятое
окно накрывало бы шапку при прокрутке.

**Сохранённая раскладка всегда чистится о текущий список окон**: набор со
временем меняется, и старая запись не должна ни оживлять снятое окно, ни
прятать новое — неизвестные id выбрасываются, недостающие дописываются со
значениями по умолчанию. Геометрия свободного режима принимается только
целиком и только числами: окно с `NaN` в ширине рисуется нулевым, и
схватиться за него мышью уже нечем. Согласованность разметки, скрипта и CSS
держит `dwp.test_web_snapshot`, раздел 8.

При смене ширины окна браузера свободная раскладка тянется пропорционально
**по горизонтали** и не тянется по вертикали: там прокрутка, а не дефицит
места, и растянутая по высоте карта перестала бы быть квадратной.

Свободный режим не включается в двух случаях: в OBS (`?bare=1`) и при
ширине экрана до 820 px. Там колонка одна, и координаты, снятые с широкого
монитора, сделали бы панель нечитаемой; окна временно идут в столбик, а
сохранённая раскладка не портится.

### Лента событий: журнала в источнике нет, он выводится

Хотелось видеть, кто кого убил, портретами. Проблема в том, что **журнала
событий в `GetRealtimeStats` нет вовсе** — ни строчки «A убил B», ни времени
последнего фрага. Есть только счётчики `kill_count` / `death_count` /
`assists_count` у каждого игрока и список зданий. Значит лента не читается, а
ВЫВОДИТСЯ из разницы между соседними опросами (`dwp/killfeed.py`) — и вместе
с ней выводится ровно та неопределённость, которой в настоящем журнале не
было бы.

Что здесь факт, а что вывод:

| | откуда |
|---|---|
| герой погиб | факт: `death_count` вырос |
| у противника фраг | факт: `kill_count` вырос |
| **кто кого убил** | вывод, и однозначный ТОЛЬКО когда в окне одна смерть и один фраг |
| здание пало | факт: позиция исчезла из числа стоящих; сторона, ярус и линия известны |

Поэтому событие несёт флаг `certain`. Замес из двух смертей и двух фрагов
разложить по парам нечем — таких полей в источнике нет, — и он показывается
замесом («трое погибли, фраги у двоих»), а не выдуманными парами. Смерть без
единого фрага у противника — это вышка, крипы, Рошан или денай; подставлять
«наверное, убил кто-то рядом» нельзя, и лента пишет «не от героя».

Расстояние до ближайшего врага СЧИТАЕТСЯ и лежит в поле `guess`, но в текст
события не идёт и на экран не выводится: координата мёртвого героя — это,
судя по слепкам, место смерти, но проверить это нечем, а «судя по» в подпись
к фрагу ставить нельзя.

**Окно склейки — 3 игровых секунды.** Опрос идёт раз в 1–2 с, а замес длится
дольше; если разбирать каждый опрос отдельно, один бой распадётся на четыре
события с разной атрибуцией. Изменения копятся и разбираются вместе — так
атрибуция получается на всём бое сразу, а не на случайном его срезе.

Проверено на настоящем матче (`dwp.test_web_snapshot` гоняет 43 минуты
завершённого матча через веб-путь) и на живом: на турнирном паблике лента
дала «Tinker убил Necrophos», «Centaur Warrunner убил Lina» и «Dire потерял
вышку t1 на линии верх» — имена и стороны сошлись. `dwp.test_killfeed`
держит инварианты: убийца и жертва из разных команд, пары не выдумываются,
смена матча не порождает залпа событий из упавших счётчиков.

Запасной путь на случай, если в ответе не окажется координат зданий: тогда
«какая именно вышка» не сказать, а «сторона, тип и ярус» — можно, и лента
показывает это без линии. Молча не показать ничего было бы хуже.

### Цвета сторон: ошибка, которую было видно только счётом

Панель раньше красила Radiant в `#3fb950`, а Dire в `#f85149` — обычная
пара «зелёный против красного». На ней держалось всё: полоса вероятности,
вклады признаков, сетка противостояний, метки на карте.

Посчитано (Machado 2009 severity 1.0 + расстояние в OKLab, тот же расчёт,
что в `scripts/validate_palette.js` навыка dataviz):

```
пара                       норма   протанопия   дейтеранопия
#3fb950 / #f85149           33.3       17.8          2.2      <- порог 6, цель 8
#5ddc7a / #d1332a           39.8       37.6         22.0
```

**2.2 при пороге 6** означает, что для человека с дейтеранопией это был
буквально один и тот же цвет — а это каждый двадцатый зритель. Глазами
такое не увидеть никогда: на нормальном зрении пара выглядит контрастной.

Сейчас стороны разведены не только тоном, но и **светлотой** (OKLCH L 0.80
против 0.57), поэтому они различимы даже когда тон пропадает. Зелёный
остался зелёным (тон 148), красный красным (тон 28) — конвенция Dota не
нарушена. Плюс к цвету везде идёт второй канал: сторона подписана словом,
Radiant всегда слева, у названий стоят кружки, а в сетке противостояний
незначимое помечено знаком «≈», а не бледностью.

Что ещё изменилось по мелочи: тёмно-красный годится как заливка, но для
мелкого текста его контраста к поверхности (3.7:1) мало — текст теперь
светлый, а цвет несёт метка рядом с ним. Полоса вероятности разделена
зазором в 2 пикселя цветом фона, а не обводкой.

Числа считает **тот же** путь `live.extract_state → build_row → predict`.
Второй реализации инференса тут нет и быть не должно: разъедутся.

Зависимостей не добавляет — сервер на `http.server` из стандартной
библиотеки. Иконки грузятся с CDN Valve; если сети нет или адрес сменился,
на их месте остаётся короткое имя героя, страница не ломается.

Для OBS: `http://127.0.0.1:8765/?bare=1` — прозрачный фон, browser source.
`--host 0.0.0.0` откроет панель всей локальной сети (по умолчанию только
этой машине).

### Как часто опрашивать: замерено на живом матче

Панель опрашивала Steam раз в 15 секунд — цифра, взятая из осторожности.
Замер (40 опросов подряд с шагом 1 с на идущем турнирном матче):

```
различных game_time из 40 опросов: 33      шаг game_time между обновлениями: 1-2 с
период обновления источника: около 1.2 с   среднее время ответа: 0.29 с
```

**То есть при опросе раз в 15 секунд двенадцать обновлений из тринадцати
выбрасывались.** Карта дёргалась не потому, что герои прыгают, а потому что
мы почти не смотрели.

Про лимит. У Steam Web API это 100 000 запросов в сутки на ключ, то есть
1.16 в секунду в среднем за сутки. Опрос раз в 2 с за 45-минутный матч —
1350 запросов, полтора процента квоты; даже круглосуточная слежка (43 200)
вдвое ниже лимита. Ниже секунды опускаться бессмысленно: источник не
обновится.

Сейчас по умолчанию **опрос раз в 2 с, запись в лог раз в 15 с** — это
разные вещи, и путать их не стоит: строки внутри матча почти дублируют друг
друга, эффективный размер выборки равен числу матчей, и раздувать лог в семь
раз значит только сделать вид, что выборки стало больше.

Две вещи, которые пришлось поправить, чтобы частый опрос не сломал признаки:

- **История трекера прореживается по игровому времени** (не чаще одной
  точки в 5 с). Иначе за час набежало бы под три тысячи точек, дек на 400
  переполнился бы, и окно «пять минут назад» стало бы считаться от начала
  дека, а не от начала матча: усечённое окно молча превратилось бы в
  выдуманное. Побочная польза — погрешность окна упала с 15 с до 5 с.
- **Иконки героев на карте не пересоздаются, а переезжают.** При
  перерисовке через `innerHTML` браузер выбрасывает элемент вместе с его
  переходом, и герой телепортируется рывком. Сохраняя элемент, мы даём CSS
  доехать до новой точки за время между опросами — движение выглядит
  непрерывным, хотя данных по-прежнему тридцать в минуту.

Одна честность вынесена прямо на страницу: сумма линейных вкладов героев
**не равна** признаку `draft_logit` и не должна — коэффициенты берутся до
`CalibratedClassifierCV`, а признак после. На слепке это −0.106 против
−0.023. Молча показать одно вместо другого было бы удобнее и неверно.

### Карта: настоящая подложка и совмещение с ней

Основной режим — **настоящая карта Dota** подложкой, поверх неё маркеры
зданий и иконки героев. Картинка (ассет Valve из репозитория `odota/web`)
скачивается при первом запуске `dwp.web` в `data/assets/`, в проект не
коммитится. Не скачалась — панель рисует свою схему и пишет об этом под
картой; всё остальное работает.

**Совмещение подобрано, а не угадано.** Экранная доля считается как
`0.5 + x · MAP_IMAGE_SCALE` (по y со знаком минус). Множитель найден
наложением всех 36 известных зданий на картинку и просмотром результата при
1.28, 1.35 и 1.42: при **1.35** метки ложатся на строения по всей карте — у
левого края, у правого, у обеих баз; 1.28 стягивает их к центру, 1.42
выносит за строения. Точность порядка радиуса метки. Сменится раскладка
карты — число надо перепроверить тем же наложением, скрипт того стоит.

Что откуда берётся:

| элемент | откуда |
|---|---|
| подложка | картинка Valve из `odota/web`, скачивается один раз |
| позиции зданий | `buildings[].x/y`, справочник `data/map_buildings.json` |
| позиции героев | `players[].x/y`, центр иконки прижат к [3%, 97%] чтобы не резалась о край |
| ломаные линий | по настоящим координатам вышек (нужны только для запасной схемы) |
| излом линии на углу | выводится из тех же координат (см. ниже) |
| река, склоны сторон | **схема**, только в запасном режиме — координат реки API не отдаёт |
| лес | **фактура**, только в запасном режиме |

**Излом линий.** Верхняя линия идёт по левому краю и сворачивает вправо у
верхнего левого угла, нижняя идёт по низу и сворачивает вверх у правого
нижнего. Прямая между крайними вышками срезала бы угол через центр карты —
так и было, и карта из-за этого не читалась. Угол не подбирается на глаз: у
пары (последняя вышка Radiant, первая вышка Dire) два кандидата, `(ax, by)`
и `(bx, ay)`; настоящий — тот, что дальше от центра, потому что линии
загибаются наружу. Вставляется только при выигрыше по радиусу больше
`CORNER_MIN_GAIN`.

Порог пришлось перемерить, когда справочник дополнился: с неполным
справочником крайние вышки далеко друг от друга и выигрыш большой, с полным
они стоят у самого угла и выигрыш падает почти вдвое.

```
справочник 31/36:  верх 1.25   низ 1.13   мид 0.96
справочник 36/36:  верх 1.09   низ 1.13   мид 0.93
```

Порог 1.15 работал только на неполном; на полном линии распрямлялись и
срезали угол — **и это поймал тест, а не глаз**. Сейчас 1.05: разделяет оба
замера с запасом с обеих сторон, миду угол по-прежнему не достаётся.

**Река была нарисована неправильно** — вдоль мида вместо поперёк. Числа при
этом были верны все до одного, а картинка бессмысленна; поймать такое можно
было только глазами на скриншоте. Поэтому есть `dwp/test_map_geometry.py`:

```bash
python -m dwp.test_map_geometry
```

Он проверяет без браузера, что река идёт из левого верхнего угла в правый
нижний (а мид — наоборот), что у верхней и нижней линий ровно по одной
точке, которой нет в справочнике (это и есть вставленный угол), что у мида
таких точек ноль, и что троны стоят по своим углам. Справочник неполный —
тест сообщает и выходит с нулём, а не падает.

### Почему разбор драфта по героям убран под раскрытие

Панель показывала десять полосок с коэффициентами героев. Выглядит
содержательно, а содержания там почти нет, и это надо было посчитать, а не
почувствовать.

К каждому коэффициенту приписана его ошибка. Признак «герой на стороне
Radiant» — это ±1 в `n` матчах из 7434, информация примерно `n/4`, значит
ошибка примерно `2/√n`. Регуляризация (`C=0.02`) коэффициенты ещё и
поджимает, так что это верхняя оценка — но порядок величины верный.

Что из этого следует на живом составе:

```
герой                коэф.    ±ош.  матчей  значим
Bane                -0.209   0.089     506  да
Hoodwink            +0.042   0.047    1775  нет
Undying             -0.109   0.091     484  нет
Largo               +0.068   0.084     562  нет
Spectre             -0.057   0.167     144  нет
...
в пределах шума: 9 из 10
```

Медиана по всем героям — 542 матча, то есть **типичная ошибка ±0.086**.
Почти любая полоска короче 0.2 — шум. И проверяются 127 героев сразу, так
что несколько «значимых» появятся случайно даже при полном отсутствии
сигнала.

Пример из жизни: **Lone Druid, +0.284 на 384 матчах.** Это самый большой
коэффициент в модели, 2.8 стандартной ошибки — в одиночку прошёл бы порог.
Но при 127 проверках порядка шести героев перевалят за две ошибки и просто
так. Плюс коэффициент не отделяет «герой сильный» от «его берут сильные
команды»: Elo учтён одним столбцом на матч, а не по пикам.

Поэтому теперь наверху **вердикт** — у кого драфт сильнее и на сколько
процентов (`sigmoid(draft_logit)`), рядом второй голос из статистики пар
Stratz, а полоски по героям — под раскрытием, блёклым помечено незначимое,
рядом с каждым числом стоит его выборка.

#### Знак у героя — это вклад в пользу стороны, а не оценка героя

Место, где панель читалась ровно наоборот, и это стоило исправить в подписи,
а не объяснять устно.

Матрица драфта — `+1` за героя Radiant и `−1` за героя Dire
(`features.draft_matrix`), поэтому в `draft_block` коэффициент умножается на
сторону, и наружу уходит **вклад в логит победы Radiant**. Отсюда:

```
собственный коэффициент героя < 0  +  героя взял Dire  =  плюс Radiant
```

Живой пример из панели: **Bristleback у Dire, +0.163 в пользу Radiant.**
Читалось как «модель считает Bristleback сильным за Radiant». На деле у него
**самый низкий одиночный коэффициент из 127**: −0.163 в среднем по ансамблю
(по сидам: −0.171, −0.212, −0.138, −0.161, −0.135). И это не артефакт
регуляризации, а прямое отражение выборки — по `data/export_draft.csv.gz`
команда, взявшая Bristleback, выиграла **45.8% из 1210 матчей** (ошибка доли
±1.4 п.п.). Логит такой доли — −0.168, то есть коэффициент почти в точности
воспроизводит сырой винрейт. Плюс достаётся Radiant ровно потому, что героя
взял соперник.

Поэтому строка в «почему» теперь называет обе стороны — «Bristleback у Dire
— в пользу Radiant», — а в пояснении к ней стоит «по выборке он в минус
своей стороне». Свести это к одной стороне нельзя: у строки два разных
смысла, и оба нужны.

Оговорка та же, что и ко всем коэффициентам выше: 45.8% — это доля побед
команд, которые героя ВЗЯЛИ, а не сила героя. Одиночный коэффициент не
отделяет «герой слаб» от «его берут в проигранных позициях» и от «его берут
команды послабее» — Elo учтён одним столбцом на матч, а не по пикам.

Драфт-модель здесь **линейная**: по одному коэффициенту на героя и ни одного
парного члена. Она физически не знает, кто кого контрит и кто с кем
сочетается, — рисовать такие стрелки «по модели» значило бы выдумывать.
Поэтому противостояния берутся из внешних данных, отдельным блоком, с
подписью источника.

Источников два, и разница между ними решающая:

| | матчей на пару | ошибка доли | значимых пар из 25 | синергии |
|---|---|---|---|---|
| OpenDota `/heroes/{id}/matchups` | ~81 | 5.6 п.п. | **2** | нет вовсе |
| **Stratz** `heroStats.matchUp` | ~3300 (у состава 5450) | 0.9 п.п. | **18** | есть |

То есть на данных OpenDota вопрос «кто кого контрит» просто **не имеет
ответа**, а на Stratz имеет. Поэтому `dwp/stratz.py` — основной источник,
`dwp/matchups.py` (OpenDota) — запасной, и панель всегда пишет, чей это
результат.

Замер на живом составе, Stratz:

```
значимых пар (перевес > 2 стандартных ошибок): 18 из 25
состав против состава: +1.9 п.п. ± 0.1 на 132 662 матчах по 25 парам  -> ЗНАЧИМО
синергия Radiant:      +1.9 п.п. ± 0.2 на  89 540 матчах по 10 парам  -> ЗНАЧИМО
синергия Dire:         -2.4 п.п. ± 0.3 на  21 373 матчах по 10 парам  -> ЗНАЧИМО
```

Незначимые клетки панель помечает «≈» — это «неотличимо от ровного», а не
«ровно»; в подсказке лежит винрейт, ошибка и размер выборки.

**Токен Stratz** берётся только из переменной окружения и никогда не
пишется в файлы проекта — `data/` уходит в бэкапы:

```bash
setx STRATZ_TOKEN ваш_токен     # получить на https://stratz.com/api
```

Справочник из 127 героев добирается шестнадцатью запросами за ~17 секунд и
кэшируется в `data/stratz/` на две недели.

### Сравнение с вероятностью Stratz на живом матче

Вопрос «а у них точнее?» на одном матче не решается — но решается на
десятке, если числа записаны на **одних и тех же минутах**. Поэтому панель
на каждом опросе спрашивает у Stratz их вероятность по тому же `match_id`
(`live.match(id:).liveWinRateValues`), показывает её рядом с нашей и пишет в
лог колонками `p_stratz` / `stratz_time`. Дальше `dwp.livecheck` печатает
раздел 4: log loss обеих моделей, Brier, средняя уверенность в победителе и
распределение расхождения.

Два ограничения, о которых панель говорит прямо:

- **Stratz ведёт живьём не все матчи.** Лиговые и высокий рейтинг — да,
  рядовой паблик может не попасть вовсе; тогда в панели «Stratz этот матч не
  ведёт», а в логе пусто. Это не сбой, и наше число считается независимо.
- **Сторона у их числа не подписана в схеме.** `winRateValues` — это,
  судя по интерфейсу Stratz, вероятность Radiant, но в GraphQL стороны нет,
  и перепутать её ничего не мешает. Допущение помечено в
  `stratz.LIVE_SIDE_IS_RADIANT` и **проверяется эмпирически**: livecheck
  смотрит, указывает ли их число на победителя в последних минутах
  досмотренных матчей, и если меньше половины — ругается и отказывается
  сравнивать, вместо того чтобы напечатать перевёрнутый вывод.

Статус на 14.08.2026: **токен работает.** Прежний отдавал 403 (истёк или был
отозван); новый принят, `heroStats.matchUp` отвечает — справочник пар на 127
героев добирается и кэшируется, сетка «кто против кого» на живом составе
показывает 18 значимых пар из 25 и «состав против состава +1.9 п.п. ± 0.1 на
132 662 матчах». Эти числа теперь идут и в блок «почему» под вердиктом по
драфту, с пометкой, что в процент модели они НЕ входят.

Чего пока нет: **сравнения вероятностей на досмотренном матче.** Живьём
Stratz ведёт лиговые матчи и высокий рейтинг; ни один из записанных нами
паблик-матчей он не вёл (`live { matches }` на момент проверки отдавал пустой
список, а по конкретному `match_id` — «этот матч не ведёт»). Код, колонки
`p_stratz` / `stratz_time` в логе и раздел 4 в `dwp.livecheck` готовы; первый
же турнирный матч под запись даст настоящие числа.

### А предсказывать это не помогло

Естественная мысль: раз парные данные есть, добавить их признаками в
драфт-модель. Проверено шагающим хронологическим протоколом (обучаемся
только на прошлом), 7734 матча, 5 шагов. Признаки — взвешенный по числу
матчей перевес по 25 парам «против» и разница синергий внутри команд:

```
                                        AUC      log_loss
герои + Elo (как сейчас)              0.5921      0.6788
+ контры и синергия (все матчи)       0.5925      0.6786
+ контры и синергия (высокий рейтинг) 0.5933      0.6782
```

AUC одного признака «контры» — **0.4964** на общей выборке. Это ровно
случайность. На высоком рейтинге чуть лучше (0.5180), то есть гипотеза
«паблики ≠ про» частично подтверждается, но выигрыш всё равно порядка
0.0006 log loss при том, что весь драфт даёт 0.0133 над базой.

Вывод: **парная статистика пабликов не переносится на про-матчи.** В панель
её ставить стоит (зрителю это интересно и числа честные), в модель — нет.
Оговорка: статистика Stratz посчитана на сегодняшней мете, а матчи в
выборке старые; для лайва это правильная сторона, для оценки на истории —
смещение. Направление смещения не в пользу признака, так что вывод от
этого не меняется.

## Мини-карта в консоли (`--map`)

По умолчанию карты нет — она включается флагом:

```bash
python -m dwp.live --watch --server-steam-id <id> --model models/live_exact.pkl --map
```

Координаты для неё в ответе уже есть и ничего не стоят: `x`/`y` лежат у
каждого игрока и у каждого здания. Рисуются стоящие здания, снесённые
здания, скопления героев (цифра = сколько в клетке, `*` = в клетке обе
стороны, то есть замес) и пунктир линий по вышкам.

Одна трудность стоила отдельной проверки. **Снесённое здание из ответа не
пропадает, но обнуляется целиком** — `team`, `type`, `tier`, `lane`, `x`,
`y`, всё. То есть по ответу видно только, сколько записей обнулилось, а не
какая вышка пала. Спасает то, что позиции зданий статичны: на слепках
**двух разных матчей 21 общее стоящее здание совпало по координатам до
четвёртого знака**. Поэтому ведётся справочник `data/map_buildings.json` —
каждый опрос дописывает туда стоящие здания, а снесённые определяются как
«есть в справочнике, нет среди стоящих».

Справочник наполняется сам и становится полным после первого же опроса
матча, в котором ещё ничего не снесено. Пока в нём меньше 36 позиций,
часть снесённых нарисовать нельзя — и под картой печатается строка о том,
сколько именно позиций известно. Молча оставить пустое место было бы тем
же молчаливым нулём, только на картинке.

Побочный вывод, важный не для картинки: у **стоящих** зданий `tier` и
`lane` на месте всегда. Значит потери вышек по ярусам в лайве считаются
точно — это то, чего сейчас нет в признаках (п. 2 в «Что доработать»).

## `gold_adv` в обучении и в лайве — разные величины

Признак `gold_adv` обучен на `radiant_gold_adv` из OpenDota. Проверено на
60 матчах: это **точно** разница сумм `gold_t`, а `gold_t[-1] ≈
total_gold` — то есть **добытое** золото, а не нетворс. Лайв же подаёт
разницу `teams[].net_worth`. Нетворс — это добытое минус потраченное плюс
стоимость предметов, и совпадать они не обязаны.

Замер на 1500 завершённых матчах, последняя минута:

```
нетворс-разница / radiant_gold_adv : медиана 1.388, МНК 1.356, остаток sd 5775
смещение в пользу ПОБЕДИТЕЛЯ      : медиана +6278 золота
знак смещения совпадает со знаком лидера в 96.0% матчей
сумма нетворса / сумма gold_t      : 0.941 (знаменатель gold_adv_norm)
```

Цена на экране (тест 500 матчей, множители 1.356 на `gold_adv` и
производные, 1.441 на `gold_adv_norm`):

```
вариант                             log_loss    brier     ECE   ср|dp|  p90|dp|
как училась (эталон)                  0.5079   0.1714   0.031        -        -
+ доля от банка x1.44                 0.5115   0.1713   0.030    0.031    0.081
доля строк, где сдвиг УСИЛИВАЕТ текущего лидера: 76.8%
```

Log loss почти не страдает (+0.0036) — и именно поэтому баг не виден по
метрикам. А **число на экране** уезжает в среднем на 3.1 п.п., p90
8.1 п.п., и почти всегда в сторону лидера. Это порядка всего бюджета
честности из `config.RELIABILITY_BANDS` (2.1 п.п. до 40-й минуты). Тот же
перекос затрагивает `nw_top_adv`, `nw_conc_adv` и знаменатель
`gold_adv_norm`.

### Ответ: получен на живых матчах, и он не тот, которого ждали

Гипотеза была, что `graph_data.graph_gold` из того же ответа — это и есть
обучающая величина. `livelog` записал обе, `livecheck` сверил обе с
`radiant_gold_adv` той же минуты. Три матча, 205 сверенных минут:

```
величина                медиана отн.  медиана |разн.|  корреляция
нетворс (сейчас)               1.704             4258      0.3922
graph_gold[-1]                 1.740             4058      0.4424
```

**Смотреть надо на корреляцию, а не на отношение.** 0.39 и 0.44 означают,
что обе величины — другой природы, а не тот же ряд в другом масштабе. Была
бы разница только в масштабе, корреляция была бы 0.98 при любом множителе.
Значит подгонка коэффициентом (та самая ×1.36) чинит не то: ошибка не в
масштабе. `graph_gold` отвергнут — он тоже нетворс.

**Причина найдена и измерена: буйбэки.** Нетворс — это предметы плюс
несвязанное золото; `radiant_gold_adv` — добытое золото. Расходятся они на
всём, что куплено и исчезло. Разбор матча 8943235603 (Team Resilience —
LGD Gaming, 65 минут):

```
итоговый нетворс OpenDota   Radiant 176519  Dire 126689   разница +49830
последнее nw_adv в лайв-логе                              разница +49880  <- лайв читает верно
итоговая разница gold_t                                           +10746
зазор                                                             +39084
буйбэков за матч 13, из них 11 у Dire
```

На 1200 командах зазор «добытое минус нетворс» объясняется на **R²=0.81**
парой (длительность, число буйбэков × уровень), с физически осмысленными
коэффициентами: **255 золота за минуту** на расходники и вагоны и
**≈119 × уровень за буйбэк** (то есть около 3000 на 25-м уровне). Буйбэки
идут в концовке и почти всегда у отстающей стороны — поэтому расхождение
растёт именно там, где на экран смотрят.

**Цена, померенная на настоящем матче** (52 минуты лога против офлайн-пути
на тех же минутах, `draft_logit` уравнен, чтобы сравнивать только
экономику):

```
|dp|: среднее 6.3 п.п.   медиана 4.1   p90 15.5   max 22.5
в 80.8% строк экран УВЕРЕННЕЕ в пользу текущего лидера
```

Это вдвое хуже офлайн-оценки в 3.1 п.п. — и понятно почему: офлайн-оценка
брала средний множитель, а настоящая ошибка концентрируется в концовке.
Показательные минуты того матча:

```
мин  экран  как училась   gold на экране  gold обучающий
 48  79.4%     63.0%              7 778             904
 62  99.2%     89.1%             28 921           4 079
 64  99.7%     97.9%             48 270           5 769
```

На 62-й минуте по добытому золоту игра была ровной (+4079), а панель
показывала перевес в 29 тысяч и 99.2%. Это ровно те камбэки, ради которых
матч и смотрят.

**Что с этим делать** — в разделе «Что доработать», пункт 0. Коротко:
подгонка множителем отменяется как заведомо неверная, вместо неё либо
восстанавливать нетворс офлайн (буйбэки в `buyback_log` есть), либо
переносить вес на признаки, у которых определения совпадают точно.

## Какую модель брать

```
models/live_exact.pkl   21 признак   ЛАЙВ — брать эту
models/live.pkl         15 признаков базовая, для сравнения
models/full.pkl         25 признаков офлайн-разбор (с XP и байбэками), live.py её отвергает
```

Для лайва — **`live_exact.pkl`**, и это стоит на умолчании у `dwp.web` и
`dwp.live`. Обоснование не «новее», а измеренное:

| | `live.pkl` | `live_exact.pkl` |
|---|---|---|
| log loss (тест, 1547 матчей) | 0.5164 | 0.5189, интервал [-0.0002, +0.0054] — **не значимо** |
| ECE (честность числа на экране) | 0.0238 | **0.0221** |
| уязвимость к подмене золота, ср. | 0.0057 | **0.0048** (−16%) |
| она же, p90 | 0.0106 | **0.0056** (−47%) |

Офлайн-метрика не отличается статистически, а два показателя, которые
важны именно в бою, лучше: число честнее и меньше едет от того, что лайв
подаёт нетворс вместо добытого золота. Если бы упор был на офлайн-разбор,
выбор был бы обратным — там `live.pkl` на волосок впереди по log loss, и
незачем платить шестью признаками.

Оговорка: на матче BoomBoys — Iron Wing `live_exact.pkl` отработала
**хуже** базовой (средняя p за победителя 27.0% против 35.4%) — она
сильнее опирается на уровни и добивания, а победители отставали и там.
Один матч ничего не решает, но записать стоит.

## Признаки, у которых определения совпадают точно (`--exact-features`)

Прямое следствие предыдущего раздела: сильнейший признак модели —
единственный, у которого определение в обучении и в лайве расходится.
Разумно перенести часть веса на признаки, у которых расхождению взяться
неоткуда:

| признак | обучение | лайв |
|---|---|---|
| `level_adv` | `xp_t` → уровень по `config.XP_TO_LEVEL` | `players[].level` |
| `lh_adv` | `lh_t` | `players[].lh_count` |
| `dn_adv` | `dn_t` | `players[].denies_count` |
| `radiant_t3_lost`, `dire_t3_lost`, `t3_adv` | имя здания в `building_kill` | `tier` у стоящих зданий |

Проверено перед тем, как писать код: `xp_t`/`lh_t`/`dn_t` есть у всех
десяти игроков в **100%** матчей, ярус вышки — в **99.9%** (16728 событий
с ярусом, ни одного без). Матч без яруса хоть у одной вышки даёт
`tower_tier_ok = False` и `NaN`, а не частичный счёт.

**Таблица XP пришлось выводить из данных.** Справочная таблица, которая
ходит по интернету, на этих матчах оказалась неверной: она завышала
уровень у 82% игроков (по ней порог 4-го уровня 1080, а в выборке есть
игрок 3-го уровня с 1132 XP). Вывод строится на жёстком неравенстве: между
последней целой минутой и концом матча уровень можно взять, но нельзя
потерять, поэтому `xp_t[-1] < порог(level+1)`, и максимум `xp_t[-1]` среди
игроков с итоговым уровнем L — точная нижняя граница порога L+1. На 77340
игроках граница практически совпадает с порогом. Проверка на тех же
данных: `level(матч) − level(из xp_t[-1])` равен 0 у 68.8%, +1 у 27.2%,
**отрицательных нет ни одного** (а они бы значили, что таблица завышает).

### Что это дало — по-честному

Парное сравнение с бутстрапом по матчам (`dwp.compare`, 1547 тестовых
матчей):

```
  метрика              A         B     B - A          95% интервал  P(B лучше)
  log_loss        0.5164    0.5189   +0.0025    [-0.0002, +0.0054]       0.034
  brier           0.1753    0.1766   +0.0012    [+0.0001, +0.0023]       0.017
  ECE             0.0238    0.0221   -0.0017       (без интервала)
```

Офлайн-качество **не изменилось**: интервал по log loss накрывает ноль.
ECE чуть лучше. То есть шесть новых признаков не окупаются сами по себе —
и не должны были: `lh_adv` и `level_adv` несут почти ту же информацию, что
`gold_adv`, только грубее.

Смысл был в другом — в устойчивости. Она измерена так: берём тестовые
матчи, считаем `p` на честных признаках, потом портим **только золото**,
подставляя нетворс-эквивалент (разница добытого минус разница потраченного
на буйбэки, по выведенной выше модели), и смотрим, на сколько уехало число
на экране. 400 матчей с буйбэками:

```
модель        признаков   ср|dp|  медиана      p90      p99      max
база                 15   0.0057   0.0000   0.0106   0.1074   0.2982
+точные              21   0.0048   0.0000   0.0056   0.0990   0.2864
                          -16.1%            -47%     -7.8%
```

**Вывод, который стоит записать честно: помогает, но не лечит.** Средняя
уязвимость упала на 16%, p90 — вдвое, а хвост (p99, max) почти не сдвинулся.
Признак `gold_adv` слишком доминирует, и пока он в лайве другой породы,
худшие случаи останутся худшими. Разводить `gold_adv` всё равно придётся —
но теперь для этого есть модель буйбэков, то есть путь (а) стал дешевле,
чем был.

Проверка проводки: реплей-стенд на модели с новыми признаками сверяет
**20 признаков из 21** и даёт `max |p_лайв − p_офлайн| = 0.0000` на 1440
строках. То есть подсчёт ярусов по стоящим зданиям совпадает с подсчётом по
событиям, а `players[].level` — с уровнем из `xp_t` через выведенную
таблицу, до последней единицы.

## Рейтинг: даёт ли Elo хоть что-нибудь, и рейтинг чего считать

Вопрос был задан прямо: «Elo реально ли что-то даёт? я видел уже много раз,
как челы без Elo выигрывают». Ответ обратный ожиданию: **рейтинг даёт
больше, чем всё остальное в драфте вместе взятое.**

Шагающий хронологический протокол по выгрузке `data/export_draft.csv.gz`,
обучаемся только на прошлом:

```
драфт-модель                     AUC
только герои, без рейтинга    0.5520
только рейтинг, без героев    0.5907
герои + рейтинг               0.6001
```

То есть 127 геройских коэффициентов добавляют к рейтингу ~0.012 AUC, а
рейтинг к героям — 0.048, вчетверо больше. Убрать рейтинг из модели стоит
+0.0144 log loss, и интервал не накрывает ноль.

Почему при этом кажется, что рейтинг не работает: **AUC 0.60 — это «прав в
шести случаях из десяти»**. Команда без рейтинга выигрывает у команды с
рейтингом постоянно, и это ровно то, что число и обещает.

Подкрутить его нечем: перебраны k от 16 до 128, усадка молодых команд,
поправка за сторону — нынешние настройки уже на пике.

### Что сработало: рейтинг ИГРОКОВ вместо рейтинга команд

Команда в паблике — фикция: тег есть, состав меняется. Считать Elo по
`account_id` и брать среднее пяти — данных на порядок больше:

```
                    объектов  матчей на объект  покрытие строк
Elo по team_id          1090              ~11           95.4%
Elo по account_id       5080              ~25          100.0%
```

Обновление после матча: ожидание считается по среднему рейтингу пятёрки,
поправка `k·(исход − ожидание)` раздаётся всем пятерым поровну. Асимметрия
(«кор виноват больше») не пробовалась — позиций в выгрузке нет.

```
драфт-модель            AUC      log loss против команд
Elo команд           0.6001
рейтинг игроков      0.6138      −0.0049 [−0.0072, −0.0026]
```

Значимо. `k = 48` (`config.PLAYER_ELO_K`), измерено: 32 → 0.6130,
48 → 0.6138, 64 → 0.6130, 80 → 0.6115, 96 → 0.6098, 128 → 0.6064. Командный
рейтинг поверх игрокового не добавляет ничего, поэтому он заменён, а не
добавлен вторым столбцом.

**Честная оговорка: до числа на экране это улучшение не дошло.** В полной
стейт-модели на слепом холдауте рейтинг игроков против рейтинга команд даёт
+0.0004 log loss — не значимо. Выигрывает предматчевая оценка, а после
десятой минуты всё решают золото и здания, и `draft_logit` в общем итоге
весит мало. В бою рейтинг игроков всё равно стоит: он лучше там, где вообще
что-то решает, и хуже нигде.

Живьём это видно строкой-замечанием: «рейтинг игроков: +68 (10 из 10
знакомы по истории)». На пабликах знакомых бывает и трое из десяти —
тогда среднее считается по знакомым, а сколько их было, написано рядом.

Какой именно рейтинг внутри модели, хранится в артефакте
(`art["rating_kind"]`), и подписи на панели берутся оттуда, а не пишутся
руками: назвать рейтинг игроков «Elo команд» значило бы соврать в
единственном месте, где виден его вклад.

```powershell
python -m dwp.train --source real ... --rating player   # умолчание
python -m dwp.train --source real ... --rating team     # как было раньше
python -m dwp.check_accounts                            # покрытие account_id
```

## Проверенная и отклонённая идея: динамический драфт

Гипотеза была естественная: `draft_logit` — статическое предматчевое число,
а состав, который скейлится, должен решать тем больше, чем дольше идёт игра.
Значит стоит завести второй логит, обученный на длинных матчах, и дать
дереву переключаться между ними по минуте.

Прежде чем строить, померено на 1547 тестовых матчах (драфт-модель их не
видела). AUC драфта против исхода, по длине матча:

```
длина           матчей     AUC          95% интервал
до 30              467  0.6343      [0.5828, 0.6825]
30-40              649  0.6142      [0.5710, 0.6588]
40-50              298  0.5505      [0.4856, 0.6136]
50+                133  0.5765      [0.4782, 0.6710]
```

Сила драфта с длиной матча **не растёт, а падает**. Интервалы широкие и
перекрываются, так что уверенно утверждать падение нельзя — но ни одна
точка не поддерживает рост, а на 40-50 минутах драфт-модель проигрывает
даже базовой ставке (log loss 0.6883 против 0.6841). Объяснение вполне
физическое: если игра всё ещё идёт на 45-й минуте, преимущество драфта уже
не сконвертировалось; длинные матчи — это по определению те, где
предматчевая асимметрия не решила.

Вторая форма той же идеи, ближе к делу: предсказывает ли драфт **камбэк**.
Матчи, где на 35-40-й минуте одна сторона вела 11k+ (336 матчей, камбэков
10, то есть 3.0%):

```
AUC драфта для предсказания камбэка: 0.5936  [0.4738, 0.7236]
драфт отстающего хуже медианы:  1.8% камбэков (168 матчей)
драфт отстающего лучше медианы: 4.2% камбэков (168 матчей)
```

Интервал накрывает 0.5, разница между половинами — это 3 камбэка против 7.
Строить на этом нельзя.

**Вывод: не реализовано намеренно.** Усиливать вес слабого сигнала —
значит добавлять шум. При этом `draft_logit` и так третий по важности
признак в модели (gain 9.7% у базовой, 10.1% у `--exact-features`; два
признака по золоту вместе дают 64-71%), то есть он не «недооценён».

**Чего это НЕ означает.** Что драфт не важен в Dota. Означает только, что
*наша* драфт-модель слишком груба, чтобы показать это: 127 геройских
коэффициентов на несколько тысяч матчей, AUC около 0.62, без синергий и
контрпиков. Правильный ход — не перевешивать слабый сигнал, а сделать
сигнал сильнее (п. 2 в «Что доработать»: эмбеддинги героев вместо
одиночных коэффициентов). Тогда вопрос про динамику стоит померить заново.

## Измерение самого лайв-пути

Всё, что этот проект знал о своей точности, было померено офлайн — на
выгрузке OpenDota, тем же кодом, что строит обучающую выборку. Точность
того, что реально показано на экране, не измерялась никогда, и измерить
её было нечем: опросы никуда не сохранялись. Две вещи это закрывают.

**`test_live_replay`** — воспроизводимость без сети. Берёт N завершённых
матчей из `data/matches`, на каждую минуту собирает ответ в схеме
`GetRealtimeStats` (`net_worth` из `gold_t`, `kill_count` из `kills_log`,
`buildings` из `tower_kills`/`rax_kills`), гонит через
`extract_state → LiveTracker → build_row → predict` и сравнивает с
офлайн-путём `features.match_state_frame` по каждому признаку и по
итоговой вероятности. Числитель одинаков по построению, поэтому любое
расхождение — это ровно цена кода лайва.

```
              ср|dp|    max|dp|
было          0.0303     0.6247
стало         0.0000     0.0000     (1440 строк, 40 матчей, 7 с мегакрипами)
```

**`livelog` + `livecheck`** — измерение с сетью, на настоящем матче.

```bash
python -m dwp.live --watch --server-steam-id <id> --model models\live_exact.pkl --log
python -m dwp.livecheck                 # добрать исходы и посчитать
python -m dwp.livecheck --offline       # только по уже добранным
```

`--log` включён по умолчанию в `--watch`. Пишется CSV на матч в
`data/live_log/<match_id>.csv`: wall-clock, `game_time`, `game_state`,
все признаки строки, калиброванная `p` и сырьё открытых вопросов
(`graph_gold_last`, `nw_adv`, `nw_total`). Формат — CSV с дописыванием, а
не JSON, именно потому что лог должен переживать падение процесса
посреди матча.

`livecheck` добирает исход по `match_id` и печатает три ответа:
reliability лайва по децилям и десятиминуткам (первая цифра, с которой
можно сверять `RELIABILITY_BANDS` — они померены офлайн и на лайв
перенесены на веру); сверку `graph_gold` и нетворса с `radiant_gold_adv`;
и `game_time` против `duration`/`pre_game_duration`.

Что уже получено:

- **`game_time` — вопрос закрыт.** Медиана (последний `game_time` −
  `duration`) = **0 с** на девяти досмотренных до конца матчах. Это часы от
  горна, как минуты обучающей выборки; 90 секунд предматчевой паузы в него
  **не входят**, признак `minute` в лайве не сдвинут. Подтверждено ещё и с
  другой стороны: до горна `game_time` отрицателен.
- **`gold_adv` — вопрос закрыт отрицательно**, см. раздел выше.
- **Калибровка лайва — ПОСЧИТАНА.** См. следующий раздел.

### Первая калибровка лайва: 8 матчей, оба исхода

Долгое время здесь стояло «считать не на чем: все записанные матчи выиграл
Radiant». Это перестало быть правдой — в `data/live_log/` накопились четыре
матча с победой Dire (8943687609, 8943719790, 8944752572, 8944819470).
`python -m dwp.livecheck` считает калибровку отдельно по каждой модели,
которой матч смотрели; у `live_exact.pkl` набралось восемь матчей, 545
строк, 4 победы Radiant против 4 побед Dire:

```
log_loss 0.3068   brier 0.0899   acc 0.8936   auc 0.9559
```

**Главное число здесь — ECE 0.126 против обещанных 0.021–0.034.** То есть

**И сразу оговорка, без которой цифру нельзя показывать.** Восемь матчей —

стоит один-два матча, и `actual` там равен 0 или 1 по построению. Такая
оценка ECE смещена вверх механически. Правильное чтение: «первое живое
измерение говорит, что расхождение заметно больше офлайнового; чтобы
назвать величину, нужно матчей тридцать». Отрезок 50–59 минут (log loss
0.84 при базе 1.29, accuracy 0.49) — это один матч, и он же тот самый
случай с буйбэками из раздела про `gold_adv`.

**Что делать дальше:** досматривать матчи до конца с `live_exact.pkl` и не
смешивать модели в одном матче — `livecheck` считает их порознь именно
потому, что смешанные строки дают среднее двух кривых за одну.

Матч, который OpenDota не разобрала (пустой `radiant_gold_adv`, у пабликов
бывает), `livecheck` теперь называет отдельной строкой: в калибровку он
идёт, в сверку золота — нет.

Кэш добранных матчей лежит в `data/live_log/resolved/`, **отдельно** от
`data/matches`: смотрят обычно паблики, а `data/matches` — обучающая
выборка про-матчей, и подмешать туда паблики значит молча испортить
следующее обучение.

## Слепой тест: оценка без знания исхода

Все замеры выше устроены одинаково: взяли модель, прогнали на тестовой
выборке, посмотрели метрику, что-то поправили, прогнали снова. Это честно
ровно один раз. К пятому кругу тест перестаёт быть слепым — исход каждого
матча уже подсмотрен через метрику, и «улучшение» вполне может оказаться
подгонкой под конкретные 1547 матчей. Изнутри такое не поймать: метрика при
этом растёт по-настоящему.

`dwp.blindtest` разводит два хода механически:

```bash
python -m dwp.blindtest --seal --n 200      # оценки записаны, исход НЕ читался
python -m dwp.blindtest --reveal --worst 12 # вскрыть и посчитать
```

Запечатывание не открывает `radiant_win` вовсе — ни для отбора матчей, ни
для метрик; отбор идёт по пригодности к реплею, а оценка считается боевым
путём `extract_state → LiveTracker → build_row → predict`. Файл закрывается
контрольной суммой, и вскрытие её проверяет: поправить модель и пересчитать
по старому конверту не выйдет. Берутся только матчи из `test_match_ids`
модели — матч, который она видела при обучении, слепым не является ни в
каком смысле.

**Результат на 200 слепых матчах** (`live_exact.pkl`, 7388 строк):

```
log_loss 0.5286   brier 0.1803   acc 0.7030   auc 0.7979   ECE 0.0474

разложение Мёрфи        brier = ненадёжность − разрешение + неопределённость
  ненадёжность      0.0028     насколько число врёт
  разрешение        0.0661     насколько модель различает матчи
  неопределённость  0.2447     brier у константы — планка, от которой польза
  навык             +0.2584    (разрешение − ненадёжность) / неопределённость
```

Разложение Мёрфи здесь важнее log loss, потому что log loss смешивает две
разные способности. Модель, всегда говорящая базовую ставку, идеально
надёжна и совершенно бесполезна: у неё разрешение равно нулю. Здесь
ненадёжность в 24 раза меньше разрешения — то есть число честное, и при
этом матчи модель действительно различает.

**Правила, которые тоже не знают исхода** (никакого обучения, для масштаба):

```
константа (base rate)          log_loss 0.6901   acc 0.5731
один драфт, без карты          log_loss 0.6889   acc 0.5551
модель                         log_loss 0.5286   acc 0.7030
«кто впереди по золоту»                          acc 0.7130   (7388 строк)
«кто впереди по вышкам»                          acc 0.7469   (4603 строки)
```

**Сторону модель угадывает не лучше правила «кто впереди по золоту»**
(70.3% против 71.3%), и это не парадокс, а описание того, чем она вообще
полезна: не выбором победителя, а честной величиной уверенности. Правило
«впереди по золоту» не умеет сказать «61%», а разница между 61% и 95% —
это и есть всё содержание оверлея.

**Когда модель определяется:**

```
определилась и больше не колебалась ниже 80% за победителя: 198 матчей из 200
  медиана: на 28-й минуте, за 4 минуты до конца
матчей, где она хоть раз давала будущему победителю меньше 10%: 15 (7.5%)
```

Последняя строка — это проспанные камбэки, и `--worst` показывает их
поимённо (худший: 0.7% за 20 минут до победы). У этих же матчей проверены
сборки, см. следующий раздел.

**Оговорка про ECE.** 0.0474 против 0.0221, померенных офлайн на всей
тестовой выборке, — но в этих 200 матчах Radiant выиграл 115, то есть 57.5%
против базовых ~52%. Перекос выборки сдвигает фактическую долю вверх во
всех децилях сразу, и в таблице reliability видно ровно это: расхождения с
0.4 до 0.9 все одного знака. На 200 матчах отличить это от смещения модели
нечем; нужен конверт побольше.

**Два других режима.** `--source livelog` вскрывает не реплей, а то, что
реально стояло на экране во время записанных матчей: числа не
пересчитываются. `--quiz` показывает положение без исхода и без числа
модели, спрашивает вашу оценку и вскрывает обе; в веб-панели то же самое
делает кнопка «слепой режим», а `--guesses` считает накопленное.

## Слепой холдаут: чтобы улучшения были настоящими

Всё, что написано выше, честно ровно один раз. Дальше начинается работа:
поменяли признак — посмотрели на тест, поменяли калибратор — посмотрели на
тест, выбрали `--exact-features` по тесту, выбрали модель для лайва по
тесту. К десятому кругу тест перестаёт быть независимым: через глаза
разработчика исход каждого матча уже просочился в решения. Это не
гипотетическая беда — раздел «Какую модель брать» построен ровно на таком
сравнении, и именно так тест и расходуется.

`dwp.holdout` прячет **15% матчей навсегда**, и обучение их не видит:

```
правило      sha1(str(match_id)) mod 1000 < 150
спрятано     1167 матчей из 7734 (15.1%)
```

**Почему хэш, а не сид.** `GroupShuffleSplit(random_state=7)` устойчив
только при неизменном наборе матчей. Добрали двести новых — разбиение
переехало целиком, матч из холдаута оказался в обучении, и «слепая» оценка
стала оценкой на виденных матчах, причём молча. От хэша разбиение не
зависит: попадание матча в холдаут определяется только им самим.

Обучение теперь исключает холдаут по умолчанию (`--no-holdout`, если очень
надо), а каждое вскрытие дописывается в `data/blind/registry.csv`:

```bash
python -m dwp.train --source real --live-features --extra-features --exact-features
python -m dwp.blindtest --seal --holdout --n 200
python -m dwp.blindtest --reveal --holdout
python -m dwp.holdout        # сколько раз в холдаут уже смотрели
```

Число взглядов — единственное, что отличает слепую оценку от подогнанной, и
держать его в голове нельзя, поэтому оно на диске.

### Что этот холдаут сразу показал: дисперсия обучения больше всего остального

Четыре модели, **одни и те же 100 слепых матчей**, 3708 строк. Три обучены
без холдаута и отличаются ТОЛЬКО сидом разбиения; четвёртая — нынешняя
боевая `live_exact.pkl`, которая эти матчи при обучении видела:

```
модель                                log_loss     auc     ECE
live_exact (сид 7, ВИДЕЛА холдаут)      0.5353  0.8037  0.0566
ho сид 7   (не видела)                  0.5720  0.7745  0.0737
ho сид 3   (не видела)                  0.5675  0.7751  0.0698
ho сид 11  (не видела)                  0.5452  0.7874  0.0349
```

**Разброс от одного лишь сида разбиения — 0.027 log loss.** Для масштаба:
весь драфт даёт 0.0133 над базой, признаки сборок 0.0012, урон 0.0003, а
урезание обучающего пула на 15% стоит 0.0019 (замерено отдельно, три
разбиения). То есть **случайность разбиения сильнее любого улучшения,
которое проект добывал, — вдвое сильнее самого драфта.**

Преимущество модели, видевшей холдаут, — всего +0.0099 против лучшей
слепой, и оно МЕНЬШЕ разброса сидов. Проверено отдельно, что это не эффект
подсматривания: разница между «видела» и «не видела» одинакова и на 158
матчах, которые старая модель видела (+0.0324), и на 42, которые лежали в
её собственном тесте (+0.0355, интервал по матчам [+0.0103, +0.0624]).
Подсматривание на этих данных стоит меньше, чем лотерея обучения.

### Прямое следствие: ансамбль

Если одиночная модель — это лотерея с размахом 0.027, её надо перестать
разыгрывать. Усреднение трёх моделей с разными сидами на тех же слепых
матчах:

```
сид 7                  0.5720
сид 3                  0.5675
сид 11                 0.5452
среднее вероятностей   0.5567     auc 0.7816   ECE 0.0576
```

Ансамбль **хуже лучшей одиночной** (0.5452) — но лучшую заранее не
выберешь. Он лучше СРЕДНЕЙ одиночной на **0.0050**, и это значимо:
интервал по матчам [−0.0063, −0.0037]. То есть три модели вместо одной
дают гарантированные 0.005 и убирают риск вытянуть плохой сид — вчетверо
больше, чем дали бы сборки, и без единого нового признака.

### Ансамбль в бою: сделано и перемерено на всём холдауте

Замер выше был на 100 матчах и трёх сидах. Теперь ансамбль работает в
`dwp.live` и `dwp.web`, а замер повторён на **всех 1167 матчах слепого
холдаута** (42 843 строки) пятью сидами — `python -m dwp.bench_ensemble`:

```
модель              log_loss    brier     ECE
ens_03                0.5258   0.1789  0.0155
ens_05                0.5270   0.1793  0.0197
ens_07                0.5326   0.1817  0.0234
ens_11                0.5280   0.1799  0.0315
ens_13                0.5293   0.1800  0.0189
среднее по одной      0.5285   0.1800
АНСАМБЛЬ              0.5233   0.1780  0.0082

ансамбль − СРЕДНЯЯ одиночная  −0.0052  95% [−0.0057, −0.0047]  P(лучше) 1.000
ансамбль − ЛУЧШАЯ одиночная   −0.0012  95% [−0.0036, +0.0023]  P(лучше) 0.791
```

Обещанные −0.0050 подтвердились до четвёртого знака: **−0.0052, интервал
[−0.0057, −0.0047]**. Критерий приёмки был «лучше средней, а не лучшей» — он
выполнен; против лучшей интервал накрывает ноль, и так и должно быть.

**А главное число здесь не log loss, а ECE.** У одиночных моделей он гуляет
от 0.0155 до 0.0315 — то есть от «честно» до «врёт на три пункта», и какая
именно модель попадётся, заранее неизвестно. У ансамбля **0.0082**, вдвое
лучше самой честной одиночной. Для оверлея это важнее сотых log loss:
ECE — это ровно то, насколько врёт число на экране.

Разброс log loss между сидами на этой выборке — 0.0068 (на прежней, из ста
матчей, было 0.027; сто матчей для такой оценки мало).

**Как устроено.** `live.load_models` принимает несколько артефактов и
возвращает обычный артефакт с ключом `members`; всё, что читало
`state_features` или `draft_coef`, продолжает работать. Три решения, которые
пришлось принять, и почему именно так:

- **усредняются вероятности, а не логиты.** На замере разницы между ними не
  было (0.5567 против 0.5567), а у каждой модели свой калибратор и своя
  обрезка хвостов: усреднять уже калиброванные вероятности законно,
  калибровать среднее заново — нет, для этого нужна отдельная выборка;
- **у каждого участника свой `draft_logit`.** Драфт-модель обучена на своём
  разбиении; подставить всем один логит значило бы усреднять не то, что
  меряли. В саму строку (и в лог) идёт среднее логитов, а каждая модель
  считает по своему;
- **вклады усредняются тоже**, иначе сумма вкладов перестанет сходиться с
  числом на экране. Коэффициенты драфта по героям усредняются только ради
  экранного разбора — в предсказание они не идут.

Умолчание в `dwp.live` и `dwp.web` теперь такое: если в `models/` лежит
`ens_*.pkl` хотя бы в двух экземплярах — берётся ансамбль, иначе
`live_exact.pkl`. Реплей-стенд на ансамбле даёт то же
`max |p_лайв − p_офлайн| = 0.0000` на 1440 строках, что и на одиночной.

```powershell
python -m dwp.train --source real --live-features --extra-features --exact-features --gold-norm add --seed 3 --out models\ens_03.pkl
python -m dwp.bench_ensemble --models models\ens_*.pkl
python -m dwp.live --watch --server-steam-id <id> --model models\ens_*.pkl
```

**Осторожно с одной вещью:** в наборе `--gold-norm add` обязателен. Команды
в старой редакции IMPROVE.md его не содержали, и обученные по ним модели
отличались от боевой на два признака; `load_models` такой набор не примет и
скажет, какое поле разошлось.

### Две попытки сделать ансамбль лучше, обе неудачные

Записаны потому, что обе выглядят очевидно правильными и будут предложены
снова.

**1. Привязать сид LightGBM к сиду разбиения.** До этого у всех пяти моделей
бэггинг и отбор признаков были одинаковы (`bagging_fraction=0.8`,
`feature_fraction=0.9` с общим сидом по умолчанию), то есть разнообразие
брали только из разных разбиений данных. Логично добавить и второе.
Сделано (`params.setdefault("seed", seed)`), перемерено:

```
набор            log_loss    brier     ECE
общий сид LGBM     0.5236   0.1781  0.0079
сид от разбиения   0.5233   0.1780  0.0082

разница −0.0003, 95% [−0.0009, +0.0002]  — интервал накрывает ноль
```

Не значимо. Изменение оставлено (оно правильнее по смыслу: участники
ансамбля не должны делить один источник случайности), но выигрыша от него
нет, и записывать его как улучшение было бы неправдой.

**2. Разнородный ансамбль: разные гиперпараметры, а не только сиды.**
Обычный совет — что ансамбль из РАЗНЫХ моделей сильнее, чем из одинаковых.
Добавлены три модели с заметно другими деревьями (`--leaves 63 --lr 0.03`,
`--leaves 15 --lr 0.08`, `--min-leaf 400 --l2 20`) и замерены восемь против
пяти на тех же 1167 матчах:

```
набор              log_loss    brier     ECE
5 сидов              0.5233   0.1780  0.0082
8 (5 сидов + 3 др.)  0.5228   0.1777  0.0085

разница −0.0005, 95% [−0.0017, +0.0006]  — интервал накрывает ноль
```

**Не окупается.** Плюс 60% времени инференса на каждом опросе — за разницу,
неотличимую от нуля. В бою остаются пять сидов; модели `models/div_*.pkl`
лежат рядом, чтобы замер можно было повторить, не переобучая (каждое
обращение к холдауту пишется в реестр, и лишних лучше не делать).

Побочное наблюдение, которое стоит записать: у одиночных «разнородных»
моделей ECE оказался заметно лучше, чем у одиночных «сидовых» (0.0119–0.0157
против 0.0155–0.0315), а у ансамбля — нет. То есть усреднение и так уже
съело почти всю нечестность, и улучшать её разнообразием больше нечем.

**Половина всей ошибки лежит в первых пятнадцати минутах, и там модель
отыгрывает у базовой ставки 4.6%.** До десятой минуты — полтора-три
процента, то есть практически ничего. После тридцатой она уже почти всё
знает, и улучшать там нечего.

Это меняет список приоритетов. Ранняя игра — единственное место, где есть
большой незанятый запас, а единственный сигнал, доступный с нулевой минуты,
— это драфт. Драфт-модель при этом слабая: 127 одиночных коэффициентов, AUC
0.607 на тесте, девять из десяти коэффициентов живого состава в пределах
шума. Значит эмбеддинги героев (п. 2 в «Что доработать») — не «когда-нибудь
потом», а главный рычаг именно для той половины ошибки, которая сейчас не
берётся ничем.

Ещё оттуда же: строки, где модель дала будущему победителю меньше 37%
(log loss > 1), — это 10.6% строк и 27.2% всей ошибки. По минутам они
распределены ровно, то есть это не «поздние камбэки», а обычная ранняя
неопределённость.

Дёрганость кривой на реальных данных: среднее изменение между соседними
минутами 4.9 п.п., медиана 3.3, p90 11.8, максимум 61.4. Прежняя оценка на
синтетике (5.0 п.п.) подтвердилась.

## Влияет ли число матчей на точность: кривая обучения

Вопрос звучал так: «стоит ли качать ещё матчи». Ответ на него нельзя дать
рассуждением — у любой модели кривая обучения рано или поздно выходит на
полку, и весь вопрос в том, дошли мы до неё или нет. Раньше здесь стояла
оценка по одной точке: «урезание пула на 15% стоит 0.0019, значит удвоение
даст порядка 0.01». Она оказалась неверной, и вот чем.

`python -m dwp.learning_curve` — пять долей обучающего пула на трёх сидах,
пятнадцать полных переобучений. Урезается **только пул**: тест внутри сида
не меняется, иначе разница между точками мерила бы заодно и то, что тест
стал меньше. Отброшенные матчи выбрасываются и из истории Elo — Elo это
признак, и оставить в нём исходы «невиденных» матчей значило бы протечку,
которая занижает эффект объёма.

```
  доля   матчей   log_loss      ±sd      ±se    brier     auc  драфт auc
  0.20     1051     0.5320   0.0029   0.0017   0.1816  0.8009     0.5506
  0.40     2101     0.5274   0.0063   0.0036   0.1798  0.8044     0.5538
  0.60     3152     0.5159   0.0041   0.0023   0.1751  0.8137     0.5832
  0.80     4202     0.5159   0.0047   0.0027   0.1757  0.8131     0.5854
  1.00     5253     0.5164   0.0063   0.0036   0.1757  0.8154     0.5935
```

**Кривая вышла на полку около 3200 матчей.** Весь размах от 1051 до 5253
матчей — 0.0156 log loss, но **последний шаг (4202 → 5253) дал −0.0005 при
двух ошибках среднего ±0.0091**, то есть ровно ничего. Три последние точки
неразличимы между собой.

Вывод, который стоит записать прямо: **добор матчей сам по себе точность
стейт-модели больше не поднимает.** Прежняя экстраполяция «удвоение даст
0.01» была получена из одной точки (−15% стоит 0.0019) и линейного
продолжения, а кривая нелинейна — на этом участке она уже плоская. Пункт
«больше матчей» из списка приоритетов надо убрать.

**Но у драфт-модели полка НЕ достигнута.** Её AUC растёт всю дорогу:
0.5506 → 0.5935, и на последнем шаге **+0.0081** — то есть данные ей всё
ещё нужны. Это ровно та модель, на которой держатся первые пятнадцать
минут, где лежит половина всей ошибки. Причина понятна: 127 одиночных
коэффициентов на несколько тысяч матчей; линейной модели с таким числом
параметров данных не хватает дольше, чем дереву.

Оговорка, без которой числа читаются неверно: подвыборка случайна **по всей
истории**, поэтому замер про ОБЪЁМ при неизменной мете. Настоящий добор
приносит ещё и свежие патчи, а старые матчи при этом устаревают — это
отдельный эффект, здесь не отделённый, и он может оказаться больше эффекта
объёма. Веса по свежести (п. 1 в «Что доработать») от этого замера не
отменяются, а наоборот.

### Проверка предсказания: выгрузка выросла до 12 500 матчей

Кривая обещала полку — выгрузка выросла вдвое с лишним, и полку удалось
проверить не экстраполяцией, а прямым замером. Ансамбль из пяти сидов
переобучен с нуля на 12 500 матчах и сравнён со старым на слепом холдауте
(1864 матча, парный бутстрап по `match_id`):

```
                        log loss
старый ансамбль (5253)    0.5192
новый ансамбль (12500)    0.5180
разница                  −0.0016   95% [−0.0038, +0.0006]
```

**Интервал накрывает ноль. Полка подтверждена прямым замером**, а не
экстраполяцией кривой. Это второй независимый способ прийти к одному и
тому же выводу, и он дороже первого: между ними целая догрузка данных.

Одна деталь, без которой вывод шире, чем следует: **докачанные матчи не
свежие, а старые** — январь–май 2026, диапазон `match_id` пошёл вниз.
Патчей в выгрузке по-прежнему два. То есть замер говорит «больше матчей ТОЙ
ЖЕ меты не помогает», и ничего не говорит про свежие патчи.

Драфт-модели объём по-прежнему полезен: именно на 12 500 матчах рейтинг
игроков обошёл рейтинг команд значимо (раздел «Рейтинг»), а на 5253 матчах
этой разницы было не различить.

## Коридор неопределённости: что показывать «на перспективу»

**С панели этот блок снят 16.08.2026** — вместе с «перспективой» целиком.
Раздел оставлен потому, что замер в нём верен и дорого достался, а таблица
по-прежнему считается и печатается: `python -m dwp.forecast --build` и
`--check`. Что вместо блока стоит на экране — вердикт: он отвечает на тот же
вопрос («и чем это кончится?») одним словом вместо трёх таблиц.

Постановка была такая: число на экране выглядит как аналитика вслед
событиям. Команда отыгралась — процент вырос, отдала — упал. От
инструмента, чья задача предсказывать, хочется другого: чтобы он говорил и
про то, чего ещё не случилось.

**Чего здесь делать НЕЛЬЗЯ**, и это надо сказать первым. Нельзя завести
второй, «прогнозный» процент рядом с основным. Калиброванная вероятность и
есть лучшая оценка исхода из доступной информации; любое число «на
перспективу» поверх неё будет либо той же величиной, либо хуже — и
показывать заведомо худшую оценку рядом с лучшей значит врать зрителю
дважды.

Что можно честно — три разные вещи, и все три измеримы.

### 1. Коридор: чем такие позиции кончались

`python -m dwp.forecast --build` прогоняет модель по **1167 матчам слепого
холдаута** (42 843 строки, ни один из них модель не видела) и складывает
таблицу: для каждой пары (отрезок минут, оценка лидера) — где окажется
оценка через 10 минут, как часто лидер меняется, как часто матч успевает
закончиться и чем позиции кончались на самом деле.

Всё считается ОТ ЛИЦА ЛИДЕРА (`p_lead = max(p, 1−p)`): так удваивается
выборка и вопрос формулируется так, как его задают вслух — «удержит ли тот,
кто ведёт».

```
минуты   оценка лидера      n   смена лидера  матч кончится  лидер выиграл
 0-10      0.50-0.60      6301        40.1%           0.1%          54.7%
 0-10      0.70-0.80      1256        11.5%           0.9%          72.9%
10-15      0.50-0.60      1651        43.2%           0.7%          55.5%
15-20      0.50-0.60      1472        44.4%           7.6%          54.6%
15-20      0.95-0.99       536         1.3%          60.4%          98.1%
20-25      0.50-0.60      1218        45.6%          24.9%          53.4%
20-25      0.90-0.95       534         2.8%          50.2%          94.2%
```

Читать это надо так. На 20-й минуте при оценке 55% **лидер сменится в 45.6%
случаев** — то есть игра не «чуть в пользу Radiant», а буквально нерешённая,
и это число говорит ровно то, чего проценту сказать нечем. А при 0.95-0.99
на 15-20-й минуте лидер меняется в 1.3% случаев и в 60% случаев матч просто
кончится за эти десять минут — там смотреть уже не на что.

Последняя колонка — **калибровка в чистом виде**: оценка лидера против того,
чем такие позиции кончались, на матчах, которых модель не видела. Расхождение
печатается на панели рядом с числом. На живом матче (30-я минута, лидер 61.9%)
история тех же позиций дала 62.7% — сошлось.

Клетки меньше 40 наблюдений не показываются вовсе: доля на такой выборке
неотличима от чего угодно.

### 2. Темп — как факт, а не как прогноз

На панели показано, сколько золота команда прибавляет в минуту за последние
пять минут и как за это время изменился счёт по фрагам. Это величины из
признаков, а не прогноз: **отстающая команда, которая последние пять минут
зарабатывает быстрее, и отстающая, которая проваливается дальше, дают в
проценте одно и то же число, а здесь — разное.**

### 3. Что ещё не разыграно

Стоящие вышки, t3, бараки и свободное золото обеих команд. Отставание в 20
тысяч при целых казармах и при снесённых — разные позиции, и это видно без
всякой статистики. Свободное золото в лайве точное (`Σ players[].gold`), и в
признаках модели его нет вовсе — то есть это ещё и то, чего модель не знает.

### А проекция темпа вперёд — не работает, и вот замер

Естественная мысль: продлить производные на десять минут и пересчитать
моделью — «если темп сохранится». Проверено на тех же 42 843 строках
холдаута (`python -m dwp.forecast --check`):

```
горизонт   ошибка по будущей оценке      log loss против исхода
           наивно      по темпу         наивно      по темпу
 5 минут   0.1267      0.1345           0.5236      0.5341
10 минут   0.1796      0.1879           0.5236      0.5542
```

**Проекция хуже наивного «оценка не изменится» по обоим вопросам и на обоих
горизонтах.** Перевес по золоту за пять минут вперёд не продлевается: он сам
возвращается к среднему, и продление накапливает ошибку. Поэтому на экран
она не идёт; код и замер оставлены в `dwp/forecast.py`
(`PROJECTION_MEASURED`), чтобы следующая попытка начиналась не с нуля и не с
той же идеи.

Второе, что этот замер подтверждает: log loss наивного «p не меняется»
против исхода — 0.5236, ровно как у ансамбля на холдауте. Иначе и быть не
могло, но это хорошая перекрёстная проверка обоих стендов.

## Вердикт: одна сторона вместо скачущего процента

Постановка была прямая: «пусть модель посмотрит три-пять минут и вынесет
ТОЧНЫЙ вердикт, кто победит, а не колеблется в зависимости от нетворса то
туда, то сюда». Требование разложилось на две части, и они разной природы.

**Часть первая — «не колебалась» — выполнима и выполнена.** Дёрганость
замерена: среднее изменение оценки между соседними минутами 4.9 п.п.,
максимум 61.4. Сторона, читаемая как «кто сейчас крупнее написан»,
меняется в среднем **2.10 раза за матч**, и только треть матчей проходит
без единой смены.

**Часть вторая — «точный» — упирается в минуту, а не в модель.** На минутах
0–10 при оценке лидера 0.50–0.60, куда попадает 6301 строка из 6315, лидер
выигрывает в 54.7% случаев. Информации о победителе там просто нет. Значит
выбор такой: либо говорить рано и часто ошибаться, либо ждать, пока
информация появится. Второе и выбрано.

**Правило переписано 16.08.2026 на «сказал один раз».** Прежняя редакция
(фиксация на T_LOCK плюс гистерезис) меняла сторону 0.88 раза за матч —
редко, но меняла. Требование было буквальным: «не должен ни разу
колебаться, даже если противоположная сторона имеет 90%; то, что он
поспешил, — вина вердикта». Гистерезис этого не даёт в принципе, потому что
он допускает смену по построению. Поэтому ветки смены в коде больше нет
вовсе.

### Правило

    z(t)          сглаженный логит вероятности, экспоненциальное окно с
                  полураспадом HALF_LIFE игровых минут
    conf(t)       σ(|z|) — уверенность, всегда ≥ 0.5
    до T_OPEN     вердикта нет, панель говорит «смотрю»
    после T_OPEN  как только conf ≥ THETA — назвать сторону z и ЗАПОМНИТЬ:
                  сторону, минуту и уверенность в тот момент
    дальше        не меняется НИКОГДА, до конца матча

Подпись под вердиктом тоже заморожена в момент вынесения: доля попаданий
берётся по той уверенности, что была при фиксации, а не по текущей. Иначе
рядом с неподвижной стороной шевелилось бы число, и это читалось бы как
«вердикт передумывает».

**Подобрано: ждать с 7-й минуты, полураспад 3 мин, порог уверенности
0.60, крайнего срока нет** (ждём столько, сколько нужно).

Сглаживание идёт по ИГРОВОМУ времени, а не по номеру опроса: панель
опрашивает раз в 2 с, холдаут даёт строку раз в минуту, и правило обязано
вести себя на обоих одинаково. Наивная запись `z = w·z + (1−w)·x` этого не
даёт: на постоянном входе она верна, а на наклоне отстаёт на `a·dt·w/(1−w)`
вместо непрерывного `a·τ`. Разницу поймал стенд — **0.12 в логитах** на
обычном разгоне оценки, то есть до трёх процентных пунктов на экране.
Поэтому взято точное решение при линейном между отсчётами входе:

    k  = 0.5^(dt/HALF_LIFE)
    z₁ = z₀·k + x₀·(1−k) + (x₁−x₀)·(1 − (τ/dt)·(1−k)),   τ = HALF_LIFE/ln2

После правки расхождение между поминутным и посекундным прогоном — 0.0137
в логитах (`dwp.test_verdict`, раздел 3).

### Где подбиралось и где мерилось

Слепой холдаут делится пополам по второму хэшу от `match_id`: **A (963
матча) — подбор правила, B (901 матч) — всё, что печатается и
показывается**. Подобрать порог на тех же матчах, на которых потом
отчитаться, значило бы отчитаться о подгонке.

Критерий подбора: максимум доли сбывшихся вердиктов **при двух
ограничениях** — медиана минуты вердикта не позже `--budget` (по умолчанию
10) и вердикт появляется не реже чем в 98% матчей. Без ограничений перебор
уходит в «молчать до 27-й минуты и говорить только наверняка»: на половине A
это 96.9% попаданий при медиане 26.0, то есть вердикт к тому времени уже
никому не нужен.

### Замер на половине B (901 матч, 20 522 минуты)

```
СБЫЛСЯ, доля матчей                   0.7533
  95% интервал                  [0.724, 0.780]
```

### Цена спешки: почему именно 7-я минута


Момент открытия почти ничего не решает: медиана вердикта всё равно 11-я

Ожидание уверенности стоит **+10.4 п.п.**

вердикт и тем чаще его не будет вовсе. Нынешний выбор 0.60 продиктован
бюджетом медианной минуты. Хотите вердикт, который сбывается в 86% случаев

## Мёртвые герои на карте: признак выведен из данных

На карте нужно было отличать убитых. В `GetRealtimeStats` нет ни флага
«жив», ни таймера возрождения — у игрока только счётчики и координаты.

Брать таблицу возрождения из интернета и подписывать её как допущение не
пришлось. Проба на живом матче (84 опроса раз в 2 с, 10 игроков, 7 смертей)
показала: **координаты убитого героя замирают в точке смерти и снова
начинают меняться в момент возрождения**. Простой совпал с таймерами Dota:

```
уровень 14   46 и 48 с        уровень 19   69 с
уровень 18   66 с             уровень 22   84 с
```

Разделение чистое: на 1300 парах соседних опросов координата **не менялась
вовсе (разница ровно 0.0) в 957 случаях**, а когда менялась — минимальный
сдвиг 1.372e-04. Дрожания в этом источнике нет: стоящий герой отдаёт тот же
float бит в бит. Порог `deaths.MOVE_EPS = 1e-5` взят заведомо ниже
наблюдённого минимума.

Правило: **мёртв = счётчик смертей вырос И координаты с тех пор стоят**.
Ошибается оно только в безопасную сторону — герой показан мёртвым чуть
дольше, чем был (ровно столько, сколько возрождённый стоит на фонтане), но
никогда живым, пока мёртв.

Чего правило не знает: подключились в середине — про уже лежащих мы не
знаем ничего, и они считаются живыми до первой смерти при нас (`known`).
**Без координат признак не ставится вовсе**: снять его будет нечем, и герой
остался бы мёртвым до конца матча — молчаливое «мёртв» хуже честного «не
знаю». В офлайн-реплее координат нет, поэтому там считается только число
увиденных смертей.

Побочная находка: `test_live_replay.payload_at` жёстко ставил
`death_count: 0`, из-за чего реплей не мог показать ни точного фрага в
ленте (только «замес»), ни мёртвого героя. Теперь смерти восстанавливаются
из `kills_log` противников (там записано и время, и кого убили), и лента в
реплее даёт 99 названных героев вместо 43.

## Эмбеддинги героев для драфта: ОТКЛОНЕНО замером

Пункт 2 из «Что доработать» был главным рычагом на бумаге: половина всей
ошибки лежит до 15-й минуты, где драфт — единственный сигнал, а драфт-модель
знает героев только поодиночке.

### Как устроена модель

Обычная факторизационная машина на кодировке «+1 Radiant, −1 Dire» здесь
НЕВЕРНА, и это стоит записать: слагаемое `<v_i,v_j>·x_i·x_j` для пары внутри
Dire даёт `(−1)(−1) = +1`, то есть синергия Dire прибавляется к оценке
Radiant. Поэтому синергия и контра разведены явно:

    score = b + w·elo
            + Σ_{i∈R} a_i − Σ_{j∈D} a_j
            + Σ_{i<j∈R} <u_i,u_j> − Σ_{i<j∈D} <u_i,u_j>
            + (Σ_R v)ᵀ M (Σ_D v),   M = A − Aᵀ

`M` антисимметрична намеренно: «i контрит j» обязано означать «j контрится
i-м» с обратным знаком. При перестановке сторон всё, кроме `b`, меняет знак.

### Замер

Шагающий хронологический протокол, 4 шага, слепой холдаут исключён целиком,
штраф подбирается на внутренней проверке внутри обучающего куска. Тёплый
старт от базовой логистической модели: иначе выходит гонка, в которой
эмбеддинги успевают запомнить выборку раньше, чем линейная часть сойдётся
(на первом заходе лучшая эпоха всегда оказывалась первой).

```
                    log_loss     auc     acc      n
база                  0.6801  0.5887  0.5659   5254
эмбеддинги dim=8      0.6831  0.5804  0.5563   5254
эмбеддинги dim=4      0.6804  0.5839  0.5609   5254
эмбеддинги dim=2      0.6810  0.5820  0.5594   5254
```

**Контрольный прогон решает вопрос окончательно.** Если выключить И
синергию, И контру, модель обязана свестись к тёплому старту. Такой прогон
даёт Δ log_loss +0.0003 [−0.0013, +0.0017], Δ AUC −0.0048 [−0.0091,
+0.0002] — **ровно те же числа, что и прогон «только контра»**. То есть
контра не даёт ничего вообще, а видимая просадка это шум самого стенда
(разница между дообучением Adam и чистым `LogisticRegression`). Синергия
сверх контроля даёт −0.0019 AUC, то есть тоже ничего.

Единственная зацепка: на ПОСЛЕДНЕМ шаге, где обучающих матчей больше всего
(5254), эмбеддинги стабильно чуть впереди — AUC 0.6115 → 0.6131, log loss
0.6745 → 0.6736. Это согласуется с кривой обучения: у драфт-модели полка не
достигнута. **Возвращаться к идее имеет смысл, когда выгрузка примерно
удвоится, и не раньше.**

    python -m dwp.draft_emb --walk 4 --dim 8 --ablate

## Восстановление нетворса: ОТКЛОНЕНО замером, но зазор измерен точнее

Самая дорогая известная неточность — `gold_adv`: обучение подаёт разницу
ДОБЫТОГО золота, лайв подаёт разницу НЕТВОРСА. Путь (а) из «Что
доработать» предлагал восстановить нетворс и переобучить.

Прежняя попытка шла через журнал покупок по каждому игроку и провалилась:
ошибки десяти игроков копились. Здесь попробовано иначе — восстанавливать
сразу КОМАНДНУЮ РАЗНИЦУ, единственную величину, которая идёт в признак:

    нетворс_adv(t) ≈ добытое_adv(t) + b₁·t + b₂·Δсмертей(t)
                                    + b₃·Δбуйбэков(t)
                                    + b₄·Δ(буйбэк×уровень)(t) + b₅·Δуровней(t)

Все пять величин есть поминутно: смерти — из `kills_log` противников
(потеря 1.5%: смерти от крипов и вышек туда не попадают), буйбэки — из
`buyback_log` со временем, уровни — из `xp_t` через `config.XP_TO_LEVEL`.

**В конечной точке это работает** (1500 матчей, подгонка на 750, замер на
750):

```
вариант                 R² на замере  |медиана| ост.  p90 ост.
зазор без поправки                 —            6487     13563
через ноль                     0.711            2381      6601
со свободным членом            0.709            2513      6756
```

Свободного члена быть не должно: на нулевой минуте зазор равен нулю по
определению, а подгонка на концах давала const = +1207 золота.

**Посреди матча поправка не держится, и это решает вопрос.** Единственная
мид-матчевая правда — записанные живьём матчи, у которых есть и поминутный
нетворс, и разобранный офлайн-матч. Подгонка по концам на них:
|ошибка| 3269 → 3770 (хуже), p90 22629 → 29767, лучше стало в 8 матчах из
14. Подгонка ПРЯМО НА НИХ с проверкой «выкинь один матч» (11 матчей, 281
минута): |ошибка| 1871 → 1656, p90 8223 → 6673, но лучше только в 5 матчах
из 11 — то есть на невиданном матче поправка не переносится.

Причина видна из коэффициентов: на концах `bb_adv` выходит +2588 золота за
буйбэк, на живых логах +7462. Величина, подогнанная по «сколько буйбэков
было за весь матч», не та же самая, что «сколько буйбэков случилось к
минуте t».

**Побочный замер, который стоит запомнить.** На тех же живых логах
|ошибка| между добытым и нетворсом ПОСРЕДИ матча — медиана 1871 золота,
против 6487 в конечной точке. **Зазор — явление в основном ПОЗДНЕЙ игры**,
и это согласуется с «до 22 п.п. на экране в концовке»: он копится
буйбэками и потерянным на смертях золотом, которых в начале нет.

И ещё одно, что мешает строить на этих данных: из 7 записей, дошедших до
конца матча, лайв-нетворс и офлайновый финальный нетворс сходятся в
пределах 15% только у ОДНОЙ. Расхождения 8804, 11341, 14778, 17028 золота
в одной и той же точке. Пока это не объяснено, калибровать одну величину
по другой — строить на песке.

    python -m dwp.goldrecon --fit --check-live
    python -m dwp.goldrecon --fit-live

## Сборки героев: шесть слотов и шансы отыграться

Постановка была такая: «команда проигрывает, но у них кор с шестью слотами
— шансы есть». Это проверяемое утверждение, и его проверили.

### Откуда берутся данные

В лайв-ответе у каждого игрока есть `items` — девять чисел: шесть слотов
инвентаря и три рюкзака (проверено на слепках; нейтральных предметов в этом
массиве нет ни одного). Справочник предметов качается из `odota/dotaconstants`
в `data/items.json`, как и подложка карты.

На истории инвентарь приходится **восстанавливать** по `purchase_log`.
Работает это механически: журнал пишет и части, и собранный предмет
(`ogre_axe`, `mithril_hammer`, потом `black_king_bar`), значит при покупке
предмета с рецептом его части из инвентаря вынимаются.

Точность восстановления замерена на конце матча, 4000 игроков:

```

наивно                                    54.9%                     +900
со списком съедаемых предметов            77.8%                     +450
```

Список `items.CONSUMED_ON_USE` — не догадка: лишним в наивном варианте чаще
всего оказывался `aghanims_shard` (1281 раз из 4000), он съедается при
покупке и слота не занимает. Проверка со стороны данных: флаг игрока
`aghanims_shard` согласуется с фактом покупки в 88.8% случаев — остаток это
шарды с Рошана, которых в журнале покупок нет вовсе.

Оставшиеся 22% расхождения — почти всегда в плюс: предмет продали, а мы
этого не видим. Для когортной статистики это смещение **в сторону
осторожности**: часть «несобранных» коров попадает в группу «собранных» и
разбавляет её, то есть настоящий эффект, если он есть, не меньше
измеренного. `dwp.test_builds` следит, чтобы цифра не ухудшилась.

```
  40+     20к+          1005       4.0%           —              —          4.1% ± 0.6
```

**Гипотеза в сильной форме не подтвердилась.** «Кор отстающих собран не
хуже кора лидера» не добавляет шансов: внутри узких полос по минуте и
размеру отставания разница **−0.6 п.п.** (8540 наблюдений против 11391), а
по когортам знак скачет — в трёх из девяти он вообще в другую сторону.
Логистическая регрессия при контроле минуты и отставания говорит то же:

```
минута                 +0.0567 ± 0.0057   z = +9.9
отставание, тысяч      −0.2186 ± 0.0073   z = −29.8
крупных предметов у кора  −0.0498 ± 0.0345   z = −1.4
перевес по крупным        −0.0024 ± 0.0246   z = −0.1
кор собрал 6+ предметов   +0.3129 ± 0.1708   z = +1.8
```

**В слабой форме — подтвердилась, и это другое утверждение.** Не «собранный
кор даёт шансы», а «**несобранный кор их отнимает**»:

```
внутри узких полос по минуте и отставанию (10 сопоставимых полос)
  кор собрал 6+ предметов:  10.7% ± 0.4   (6495 наблюдений)
  кор собрал меньше шести:   6.4% ± 1.1   ( 487 наблюдений)
```

Разница +2.9 п.п. при ошибке около 1.2 — примерно две с половиной ошибки.
Но группа «меньше шести» — это 2% всех наблюдений и почти вся она сидит на
20-25-й минуте: к тридцатой шесть предметов есть у всех, и разрез
вырождается. Поэтому на экране это осторожная пометка, а не обещание.

**Проверка со стороны слепого теста.** В 15 матчах из 200 модель давала
будущему победителю меньше 10%. Сборки в момент худшей оценки: у 8 из 15
кор победителя был собран не хуже кора лидера, у 7 — хуже. То есть камбэки
этими 53% против 47% не объясняются вовсе.

### Не клетками, а кривой

Первая версия отвечала девятью клетками и молчала на 19-й минуте при
отставании 4900 — граница есть граница. Сетка расширена до шестнадцати
клеток (с 10-й минуты и с 2к отставания, 41039 наблюдений на 7717 матчах),
а поверх тех же наблюдений обучена логистическая регрессия:

```
на 1930 отложенных матчах: log loss 0.4309 против 0.4799 у константы, AUC 0.723
  минута                          +0.0251
  отставание, тысяч               -0.2525
  крупных предметов у кора        +0.0482
  их перевес над кором лидера     -0.0246
```

Теперь панель показывает крупно гладкое число (оно есть в любой точке и не
прыгает ступенькой на границе), а под ним — сырую долю по когорте с
выборкой. Расходятся — значит клетка широкая, и это видно, а не спрятано.

Разбиение на обучение и проверку — по матчам: одно наблюдение на матч на
когорту, до трёх наблюдений с одного матча, и разносить их между
обучением и проверкой значило бы подсмотреть исход.

**Область определения ограничена намеренно.** Логистическая регрессия с
радостью продолжит прямую на третью минуту при отставании в 500 золота и
выдаст осмысленно выглядящее число там, где отставания ещё не существует
как явления. Вне диапазона наблюдений (минута ≥ 10, отставание ≥ 2000)
модуль молчит, и `dwp.test_builds` это проверяет.

Знак коэффициентов стоит прочитать. «Минута» положительная: если ты всё
ещё отстаёшь на 40-й, а не проиграл, отставание для тебя не смертельно.
«Крупных предметов у кора» +0.048 — слабо в ожидаемую сторону. «Перевес
над кором лидера» −0.025 — в обратную, и это ровно тот же вывод, что и по
когортам: собранность кора отстающих сама по себе шансов не добавляет.

### Признаки по сборкам в модель не добавлены — вот замер

`python -m dwp.export --what extras` кладёт девять поминутных величин
(стоимость предметов, крупные предметы, сборка кора, свободное золото), а
`python -m dwp.bench_extras` меряет прирост парным бутстрапом по матчам.
Семь разбиений:

```
сид        1       3       5       7      11      13      17
разница -0.0026 -0.0014 -0.0003 -0.0018 +0.0008 -0.0016 -0.0016   (log loss)
```

Среднее −0.0012, знак в пользу сборок в шести разбиениях из семи. Для
масштаба: весь драфт даёт 0.0133 над базой, а разброс между разбиениями при
неизменных данных — 0.0079, то есть **впятеро больше эффекта**.

Не добавлены намеренно. Девять новых величин — это девять новых способов
разъехаться между обучением и лайвом, а расхождение уже есть и стоит дорого
(раздел про `gold_adv`): в лайве стоимость предметов точна, а на истории
восстановлена с медианой ошибки 4578 золота на командной разнице. Платить
такой риск за 0.0012 не стоит. Панель показывает сборки рядом с числом и
честно пишет, что модель их не видит.

### Побочный замер: восстановить нетворс офлайн не вышло

Пункт 0 в «Что доработать» предлагает путь (а): восстановить нетворс
поминутно на истории и переобучить, чтобы обучение и лайв говорили об одной
величине. Журнал покупок даёт для этого всё: нетворс = стоимость предметов
плюс свободное золото, а свободное золото = добытое минус потраченное.
Замерено на 400 матчах, конец матча:

```
нетворс ИГРОКА:            медиана ошибки −438,  |медиана| 1052,  |p90| 2701
РАЗНИЦА нетворса команд:   медиана ошибки −2778, |медиана| 7546,  |p90| 14163
                           корреляция 0.9482, знак совпал в 96.8%
для сравнения, потолок точности самих полей OpenDota
(total_gold − gold_spent против gold):        |медиана| 840
```

**Это отрицательный результат, и он важен.** На одном игроке ошибка
сравнима с шумом самих данных, но по десяти игрокам она не сокращается, а
накапливается: |медиана| 7546 золота на командной разнице — больше, чем то
расхождение, которое путь (а) должен был устранить (4258 на живых матчах).
Восстановление нетворса из журнала покупок как замена признака не годится.
Что осталось от этой работы: модель трат сходится с `gold_spent` при
корреляции 0.9757, и это можно использовать иначе — например, считать
свободное золото командой, которое в лайве известно точно.

## Урон: в лайве его нет, а в истории он ничего не добавляет

Вопрос был: «статистика урона прямо в матче тоже должна что-то весить».
Ответ распадается на два, и они разные.

**В лайве урона нет.** `python -m dwp.damage --check`: в ответе
`GetRealtimeStats` нет ни одного поля со словами damage, dmg, healing, hits
или stun — проверено на двух живых слепках. Поля игрока целиком:

```
abilities, accountid, assists_count, death_count, denies_count, gold,
heroid, items, kill_count, level, lh_count, name, net_worth, playerid,
team, team_slot, x, y
```

То есть признак по урону в бою получал бы `NaN` на каждой строке — ровно
то, за что `live.py` отвергает модели, обученные с XP. Если Valve поле
добавит, `--check` это скажет.

**В истории урон есть в двух видах, и оба неполные.** Итоговые
`hero_damage` и `tower_damage` — одно число за матч, поминутного ряда нет;
подставить их в признак нельзя, это утечка из будущего (на 20-й минуте мы
знали бы итог 45-й). А вот `teamfights[]` даёт `start`, `end` и `damage`
каждого участника, и из этого поминутный ряд собирается честно. Покрытие:

```
доля времени матча внутри стычек: медиана 0.158
урон в стычках против итогового hero_damage: корреляция 0.7963,
                                             отношение медиан 0.403
```

То есть это урон В ЗАМЕСАХ — около 40% всего, — но зато у него есть время.

**Замер: не весит ничего.** Семь признаков (перевес по урону, доля урона,
хилл, урон на добытое золото, золото за стычки, выкупы в стычках, минут с
последней стычки), парный бутстрап по матчам:

```
сид 7:  разница −0.0003   95% [−0.0021, +0.0014]   не значимо
сид 3:  разница −0.0004   95% [−0.0029, +0.0018]   не значимо
```

Ноль в пределах измерения. Объяснение простое и его стоит записать: урон в
замесах — это следствие того, что модель уже видит. Выигранный замес
приходит к ней золотом, фрагами и вышками через минуту-другую; отдельного
знания в урон почти не остаётся. Разница между «нанёс много урона» и
«выиграл замес» — это как раз то, что не конвертировалось.

Вывод для панели: показывать урон нечем и незачем — вместо этого в блоке
«чего модель не знает» прямо написано, что урона в источнике нет.

### Аудит 16.08.2026: что нашлось в коде

Проверялось так: `pyflakes` и `vulture` по всему пакету, граф импортов
(кто кого зовёт, кого не зовёт никто), сверка ключей снимка с тем, что
читает страница, сверка классов и id в CSS с разметкой, разбор скрипта
парсером JS, поиск типовых ловушек по AST (голый `except`, изменяемые
значения по умолчанию, `== None`, `open()` без кодировки).

Настоящие ошибки, которые нашлись и исправлены:

1. **Вероятность Stratz кэшировалась без привязки к матчу.** Переключили
   матч внутри тридцатисекундного окна — и в лайв-лог нового матча уходила
   колонка `p_stratz` от ПРЕЖНЕГО. То есть в сравнение «кто врал больше»
   подставлялось чужое число. Кэш теперь держится за `match_id`.
2. **Гонка при смене матча.** Опрос длится ~0.3 с; если переключение
   попадало внутрь, снимок прошлого матча публиковался уже с новым `sid` —
   панель молча показывала чужие числа, выглядящие свежими. Введён номер
   поколения: снимок публикуется, только если матч за время опроса не
   сменился.
3. **`/api/games` вешал страницу на полторы минуты** — см. выше.
4. **Слепой режим не прятал ленту событий**, хотя разметка это
   предполагала: `drawFeed` выполнялся ПОСЛЕ и возвращал блок обратно.
   Решено в другую сторону: слепой режим прячет теперь ровно вердикт, а
   счёт, карта, сборки и лента — это факты матча, по которым зритель как
   раз и должен называть своё число.
5. **Пропала разметка двух блоков.** Классы `.kpi` (четыре счётчика в
   разделе «данные и обучение») и `.chance` (рамка ввода догадки в слепом
   режиме) были удалены из CSS вместе со снятыми блоками, а места, где они
   применяются, остались. Восстановлены.
6. **Подпись «Elo команд» на модели с рейтингом игроков** — в двух местах,
   на панели и в консольном разборе вкладов. Теперь подпись берётся из
   `art["rating_kind"]`, а не пишется руками.

Мёртвое, что вычищено: разбор вкладов, история вероятности, сетка
противостояний, число Stratz и ещё четыре поля считались на каждый опрос и
выбрасывались браузером — снимок похудел примерно на треть. Из CSS убрано
двадцать правил от снятых блоков, из модулей — четырнадцать неиспользуемых
импортов и две функции в `accuracy.py`, которые никто не звал.

Чего НЕ нашлось: ни одного голого `except`, ни одного изменяемого значения
по умолчанию, ни одного `open()` без кодировки, ни одного сравнения с
`None` через `==`. Тридцать «молчащих» `except ... : pass` — это все один и
тот же `stream.reconfigure(errors="replace")` в начале каждого `main()`.

Чтобы этот класс поломок ловился сам, в `dwp.test_web_snapshot` добавлен
раздел 8: он сверяет, что каждый id, к которому лезет скрипт, есть в
разметке, что окна раскладки перечислены и там и там, что у каждого маркера
свободного режима есть правило в CSS (маркер без правила существует в DOM,
но имеет нулевой размер — схватиться нельзя, а на глаз не отличить), и что
скрипт вообще разбирается парсером JS (`pip install esprima`; нет пакета —
раздел честно говорит, что синтаксис не проверен).

**Написано, но ни разу не выполнялось:**

- `collect` против живого OpenDota. Ретраи на 429 с разбором
  `Retry-After`, ретраи на 5xx, обработка ответа «200, но не JSON» —
  код есть, на живом API не проверен. (Тот же клиент `dwp.http` теперь
  использует и `live`.)
- `check_schema` на реальных данных. Вывод про `team = victim`
  подтверждён только против собственного генератора, который под эту же
  конвенцию и написан. **Это главный кандидат на расхождение.**
- `--dump` на живом ответе (слепки в `data/` сняты раньше и лежат).
- Сравнение нашей вероятности с вероятностью Stratz на досмотренном матче:
  ни один из записанных паблик-матчей они не вели.

Фикстура лайва построена по той же предполагаемой схеме, которую ищет
`extract_state`. Тест доказывает, что экстрактор работает на этой схеме и
корректно деградирует. Он **не** доказывает, что `GetRealtimeStats`
выглядит так.

## Ограничения

**Задержка.** По репортам разработчиков `GetLiveLeagueGames` и
`GetRealtimeStats` заметно отстают от реального времени. `GetTopLiveGame`
идёт без задержки, но показывает не все матчи. Плюс задержка самой
трансляции. Для оверлея приемлемо.

**Рошан в лайве** определяется по переходу таймера респавна из нуля в
положительное значение. Кто именно убил — из этого источника не следует,
и подставлять «наверное, лидер» нельзя. Поэтому `roshan_radiant` и
`roshan_dire` в лайве остаются `NaN`, заполняется только время с
последнего Рошана. Подключились к игре в середине — ранние Рошаны
потеряны, это видно по `NaN`.

**Сдвиг распределения между обучением и лайвом.** Модель училась на
полной истории Рошанов из `objectives`, а в лайве получает `NaN`.
Насколько это стоит качества — не измерено.

**Метрики на строках выглядят точнее, чем есть.** Поэтому `n_test_matches`
печатается рядом с `n_test_rows`. Доверительные интервалы считать надо по
матчам; сейчас они не считаются вообще — это дыра.

**Про-матчей мало** — несколько тысяч в год, и мета сменяется каждым
патчем. Переобучение после каждого патча обязательно. Весов по свежести
сейчас нет, все матчи равнозначны.

**Кривая дёргается.** Среднее поминутное изменение вероятности —
5.0 п.п. (медиана 4.7, p90 8.2). Для оверлея это на верхней границе
приличного. Причина — шум золота в генераторе (σ=950 за минуту), который,
вероятно, выше реального. На реальных данных перемерить обязательно;
если подтвердится — сглаживать кривую для показа, но **не** сглаживать
признаки, иначе поедет калибровка.

**XP на синтетике ничего не даёт**: с XP log loss 0.4269, без XP 0.4275 —
разница в пределах шума. Это артефакт генератора, где
`xp_adv = 1.15·gold_adv + шум`, то есть шумный дубль золота. На реальных
данных XP несёт независимую информацию (уровни, ульты), и вывод сюда
переносить нельзя.

**Рейтинг знает не всех.** Считается он теперь по `account_id` (среднее
пятерых, см. «Рейтинг»), и это чинит прежнюю беду с переездами ростеров
между тегами. Но игрока, которого в выгрузке не было, рейтинг не знает, и
среднее тогда считается по знакомым; сколько их было из десяти — написано
на экране. На пабликах бывает и трое.

**Метрики на строках выглядят точнее, чем есть** — повторено намеренно:
это единственное место, где легко обмануться. Строки внутри матча
скоррелированы, эффективный размер выборки — число матчей. Все интервалы
в этом документе считаны бутстрапом по `match_id`; если где-то встретится
интервал по строкам, ему верить нельзя.

**Не читайте память клиента Dota 2 ни при каких условиях.** Единственный
легальный источник реального времени для своей игры — Game State
Integration.

## Почему это не годится для ставок

Отдельным разделом, потому что «калиброванная модель» звучит как
достаточное условие. Оно не достаточное.

1. **Вы структурно позже рынка.** `GetRealtimeStats` отстаёт от
   реального времени, `GetTopLiveGame` показывает не все матчи, плюс
   задержка трансляции. Букмекер сидит на официальном фиде. Догнать
   задержку оптимизацией кода нельзя — она в источнике.

2. **Калибровка ≠ эдж.** Быть честным на 70% и обыгрывать линию — разные
   вещи. Нужна не точность, а систематическое расхождение с рынком
   больше маржи. Маржа на киберспорте обычно выше, чем на футболе.
   Модель на такое расхождение не проверялась, и проверить его на
   исторических данных без исторических линий невозможно.

3. **Модель не знает половины контекста.** Ход бан-фазы, замены и
   стендины, дисконнекты и паузы, техническая переигровка, форма
   конкретных игроков, мета первых недель патча. Всё это рынок учитывает,
   а модель — нет.

4. **Мета устаревает молча.** Коэффициенты героев после патча
   неправильны, но метрики на старом тесте этого не показывают. Модель
   будет уверенно врать, пока её не переобучат.

5. **Строковые метрики завышают уверенность.** 31 тысяча строк — это
   800 независимых наблюдений. Любая оценка эджа, посчитанная по строкам,
   переоценена в несколько раз.

6. **Матч-фиксинг существует** в нижних лигах, и модель на него не
   рассчитана в принципе.

7. **Steam Web API имеет условия использования.** Проверьте их до того,
   как строить на этом что-то коммерческое.

Для оверлея пункты 1–5 — терпимые неточности. Для ставок каждый из них
по отдельности достаточен, чтобы потерять деньги.

зритель. Путь через журнал покупок закрыт замером, путь через модель
буйбэков не пробован. Пока не разобрано, почему лайв-нетворс расходится с
офлайновым даже в одной точке (из семи записей сошлась одна), любая

**4. Калибровка лайва на тридцати матчах ОДНОЙ моделью.** Не улучшение

есть 13 матчей четырьмя разными моделями, и складывать их нельзя. Это
единственный замер, который меряет то, что видел зритель, и он до сих пор
не сделан.

Отдельный список, потому что его легко перепутать с предыдущим. Точность

   ECE 0.0082 против 0.0155–0.0315 у одиночных.
10. **Досмотреть тридцать матчей ОДНОЙ моделью.** Единственный замер,
    которого по-прежнему не хватает, — калибровка лайва. Сейчас в логе 13
    матчей с добранным исходом, но записаны они четырьмя разными моделями
    (`base_b`, `exact_b`, `live`, `live_exact`), и считать их одной кучей
    нельзя: получится среднее по четырём разным кривым. Теперь умолчание —
    ансамбль, значит новые записи пойдут под одним именем; тридцати матчей
    хватит, чтобы назвать ECE лайва, а не гадать между 0.126 (на восьми
    матчах) и обещанными офлайн 0.021–0.034.
