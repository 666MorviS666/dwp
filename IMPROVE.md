какому признаку считать, что стало лучше. Числа, на которых всё это стоит,
лежат в `dwp/README.md` — здесь только ссылки на них.

Список выше писался в расчёте на то, что резервы есть. Их проверили, и

| пункт | что сделали | итог |
|---|---|---|
| шаг 2: эмбеддинги героев | синергия + контра низкого ранга, ранги 2/4/8, шагающий протокол, штраф по внутренней проверке | **вклад НУЛЕВОЙ.** Контрольный прогон с выключенными синергией и контрой дал те же числа, что «только контра» |

**Что из этого следует практически.** Быстрых рычагов у точности не

1. **Больше матчей для ДРАФТ-модели.** Единственный пункт с

   матчей больше всего (AUC 0.6115 → 0.6131). Обе линии сходятся в одно:
   драфту не хватает данных, а не параметризации.
2. **Разобраться, почему лайв-нетворс и офлайновый расходятся.** Из семи
   записей, досмотренных до конца матча, лайв и офлайн сходятся в пределах
   15% только у ОДНОЙ; расхождения 8804, 11341, 14778, 17028 золота в
   одной и той же точке. Пока это не объяснено, чинить `gold_adv`
   калибровкой одного по другому бессмысленно — обе величины под вопросом.

**Что сделано вместо точности.** Дёрганость числа на экране — отдельная
беда, и она устранима без единой сотой log loss: вердикт (см. ниже)
сокращает смены стороны с 2.10 до 0.88 за матч. Для зрителя это заметнее,
чем сотые доли, которых всё равно больше нет.

## Шаг 0. Вердикт — СДЕЛАНО

Постановка: «пусть посмотрит три-пять минут и вынесет ТОЧНЫЙ вердикт, кто
победит, а не колеблется в зависимости от нетворса то туда, то сюда».

**Как разложилось.** «Не колебалась» — инженерная задача, решена.
«Точный» — упирается в информацию, а не в код: на минутах 0–10 при оценке
лидера 0.50–0.60 лидер выигрывает в 54.7% случаев, и никакое правило из
этого «точно» не сделает.

**Что сделано.** `dwp/verdict.py`: сглаживание логита по ИГРОВОМУ времени
(рамп-инвариантная дискретизация — иначе панель и холдаут разойдутся
молча) плюс гистерезис. Подбор на половине A слепого холдаута, замер и
таблица попаданий — на половине B.

```
                              вердикт   сырой процент
верных минут                   0.7267          0.7405
смен стороны за матч             0.88            2.10
матчей вообще без смен          0.441           0.329
верен в момент фиксации        0.6254
верен на последней минуте      0.9878
```

**Критерий приёмки был «меньше смен без заметной потери точности»** —
выполнен: смен в 2.4 раза меньше, точность ниже на 1.4 п.п.

Воспроизвести и перенастроить:

```powershell
python -m dwp.bench_models                     # кэш вероятностей
python -m dwp.verdict --tune --frontier        # подбор и замер
python -m dwp.verdict --tune --t-lock 8        # фиксировать позже
python -m dwp.verdict --tune --tolerance 0.03  # неподвижнее, но грубее
```

Ключ `--frontier` печатает обе цены сразу: цену неподвижности (порог смены
от 0.50 до «не менять») и цену спешки (фиксация с 3-й минуты по 10-ю).
Смотреть в него ПЕРЕД тем, как менять умолчания.

## Правила, без которых улучшение не считается улучшением

Их четыре, и каждое куплено ошибкой.

1. **Мерить парным бутстрапом по матчам, а не по строкам.** Строки внутри
   матча скоррелированы; интервал по строкам выходит вшестеро уже
   настоящего и объявляет значимой разницу, которой нет. Инструмент:
   `dwp.compare` для двух артефактов, `dwp.bench_extras` для наборов
   признаков.

2. **Ничего не принимать по одному прогону.** Разброс log loss между
   полностью переобученными моделями, отличающимися ТОЛЬКО сидом
   разбиения, — **0.027**. Весь драфт даёт 0.0133. То есть один прогон
   ничего не доказывает; нужно несколько сидов и усреднение.

3. **Не расходовать слепой холдаут.** 15% матчей спрятаны от обучения
   навсегда (`dwp.holdout`). Смотреть туда — на развилках, а не после
   каждой правки: каждое вскрытие пишется в `data/blind/registry.csv`, и
   чем их больше, тем меньше в холдауте слепоты.

4. **Отрицательный результат записывать в README с числами.** Он дороже
   положительного: экономит следующему заходу неделю. Половина этого файла
   существует только потому, что предыдущие отрицательные результаты были
   записаны.

## Шаг 1. Ансамбль из нескольких сидов — СДЕЛАНО

Оставлено в списке как образец того, чем кончилась гипотеза, и как это
воспроизвести.

**Зачем было.** Единственное улучшение, которое уже было замерено и не
требовало ни новых данных, ни новых признаков. Причина проста — одиночная
модель это розыгрыш лотереи, и усреднение убирает розыгрыш.

**Что сделано.** `live.load_models` принимает несколько артефактов и
возвращает обычный артефакт с ключом `members`; усредняются вероятности,
у каждого участника свой `draft_logit`, вклады усредняются тоже. Умолчание
в `dwp.live` и `dwp.web`: ансамбль `models\ens_*.pkl`, если он обучен.

```powershell
foreach ($s in 3,5,7,11,13) {
  python -m dwp.train --source real --live-features --extra-features `
    --exact-features --gold-norm add --seed $s --out "models\ens_$('{0:d2}' -f $s).pkl"
}
python -m dwp.bench_ensemble --models models\ens_*.pkl
```

**ВНИМАНИЕ на `--gold-norm add`.** В прежней редакции этого файла его в
командах не было, и обученные по ним модели отличались от боевой на два
признака. `load_models` такой набор не примет и скажет, какое поле
разошлось, — но час обучения при этом уже потрачен.

**Что получилось** (1167 матчей слепого холдаута, 42 843 строки):

```
модель              log_loss    brier     ECE
среднее по одной      0.5285   0.1800   0.0155-0.0315 (гуляет)
АНСАМБЛЬ              0.5233   0.1780   0.0082

ансамбль − СРЕДНЯЯ одиночная  −0.0052  95% [−0.0057, −0.0047]  P 1.000
ансамбль − ЛУЧШАЯ одиночная   −0.0012  95% [−0.0036, +0.0023]  P 0.791
```

Критерий приёмки был «лучше средней, а не лучшей» — выполнен. Обещанные
−0.0050 подтвердились до четвёртого знака.

**Что оказалось важнее log loss.** ECE: у одиночных моделей он гуляет от
0.0155 до 0.0315, у ансамбля 0.0082. Для оверлея это главное число — оно и
есть «насколько врёт процент на экране».

**Две попытки улучшить ансамбль, обе неудачные — не переделывать.** Числа в
README, раздел «Две попытки сделать ансамбль лучше»:

- привязать сид LightGBM к сиду разбиения (чтобы бэггинг у участников тоже
  различался): −0.0003, интервал [−0.0009, +0.0002] — не значимо. Изменение
  оставлено как более правильное по смыслу, но выигрыша нет;
- разнородный ансамбль (5 сидов + 3 модели с другими гиперпараметрами):
  −0.0005, интервал [−0.0017, +0.0006] — не значимо, при +60% времени
  инференса на каждом опросе. В бою остались пять сидов.

Флаги `--leaves`, `--lr`, `--min-leaf`, `--l2` у `dwp.train` заведены ровно
для этого замера. Подбирать ими гиперпараметры по тесту не надо: разброс от
сида разбиения (0.0068 на холдауте) больше типичной разницы между разумными
наборами, и «улучшение» окажется шумом.

## Шаг 2. Ранняя игра: эмбеддинги героев вместо 127 коэффициентов

**Зачем.** Ошибка разложена по фазам, и она распределена совсем не так, как
кажется во время матча:

```
до 15-й минуты   50.0% всей ошибки   модель отыгрывает у базы   4.6%
15-30            37.5%                                          25%
после 30-й       12.5%                                          53%
```

Половина всей ошибки лежит там, где модель почти бесполезна. До десятой
минуты она отыгрывает у базовой ставки полтора-три процента — то есть
практически ничего. И это объяснимо: золота ещё нет, вышек нет, а
единственный доступный сигнал — драфт. Драфт-модель при этом слабая: 127
одиночных коэффициентов, AUC 0.607, девять из десяти коэффициентов живого
состава в пределах шума.

**Что делать.** Заменить одиночные коэффициенты на эмбеддинги малой
размерности (8–16 на героя) с парными взаимодействиями. В лоб парные
признаки не годятся: ~15 000 пар на несколько тысяч матчей — гарантированное
переобучение. Варианты: факторизационная машина, либо матричное разложение
винрейтов пар, либо небольшая сеть с эмбеддингами и скалярным произведением.

Данные уже готовы: `data/export_draft.csv.gz` — одна строка на матч, ±1 за
героя, плюс `elo_div400`, плюс `start_time` для хронологического протокола.

**Как проверить.** Шагающим хронологическим протоколом (обучаемся только на
прошлом), как это уже сделано для парных данных Stratz — код можно взять из
`dwp/eloscale_experiment.py`, там ровно такой протокол на пяти шагах.

**Критерий приёмки:** AUC драфт-модели заметно выше 0.607 на шагающем
протоколе И log loss стейт-модели на холдауте улучшился. Второе важнее:
драфт входит в стейт-модель признаком `draft_logit`, и улучшение драфта само
по себе ничего не стоит, если не доходит до числа на экране.

**Чего ждать.** Ограничение сверху видно из тех же данных: подстановка
истинного логита генератора даёт 0.578 против 0.634 у нынешней драфт-модели
на синтетике. На реальных данных потолка не знает никто, но порядок — те же
несколько сотых, то есть заметно больше всего, что дали признаки состояния.

## Шаг 3. Развести `gold_adv`

**Зачем.** Самая дорогая известная неточность: обучение видит ДОБЫТОЕ
золото, лайв подаёт нетворс. На реальном матче это до 22 п.п. на экране, в
81% строк в пользу лидера, и растёт именно в концовке — там, где смотрят.

**Чего НЕ делать** (проверено и отклонено, числа в README):

- подгонять множителем ×1.36 — корреляция 0.39 говорит, что величина другой
  природы, ошибка не в масштабе;
- брать `graph_gold` из ответа — это тот же нетворс;
- восстанавливать нетворс из журнала покупок — ошибка на игроке 1052
  золота, но по десяти игрокам копится до 7546 на командной разнице, что
  больше устраняемого расхождения.

**Что осталось.** Модель буйбэков: зазор «добытое минус нетворс» объясняется
на R²=0.81 парой (длительность, число буйбэков × уровень) — около 255 золота
за минуту на расходники и около 119 × уровень за буйбэк. Восстановить
нетворс поминутно этой моделью и переобучить.

**Как проверить.** По конечной точке: восстановленный нетворс против
фактического `net_worth` в конце матча, на всех 7734 матчах. Порог — лучше,
чем 7546 медианы |ошибки| на командной разнице (столько даёт журнал
покупок), и лучше, чем 4258 (столько даёт нынешнее расхождение). Если модель
буйбэков не побивает 4258 — путь тупиковый, и это надо записать.

## Шаг 4. Больше матчей — ЗАМЕРЕНО И ОТКЛОНЕНО

Здесь стояло: «урезание пула на 15% стоит 0.0019, значит удвоение выгрузки
даст порядка 0.01 — больше, чем любой признак». **Это оказалось неверно**, и
неверно ровно тем способом, от которого этот файл и предостерегает: вывод
был получен линейной экстраполяцией ОДНОЙ точки.

`python -m dwp.learning_curve` — пять долей пула на трёх сидах, пятнадцать
полных переобучений, около четверти часа:

```
  доля   матчей   log_loss      ±sd      ±se     auc  драфт auc
  0.20     1051     0.5320   0.0029   0.0017  0.8009     0.5506
  0.40     2101     0.5274   0.0063   0.0036  0.8044     0.5538
  0.60     3152     0.5159   0.0041   0.0023  0.8137     0.5832
  0.80     4202     0.5159   0.0047   0.0027  0.8131     0.5854
  1.00     5253     0.5164   0.0063   0.0036  0.8154     0.5935
```

**Кривая вышла на полку около 3200 матчей.** Последний шаг (4202 → 5253) дал
−0.0005 при двух ошибках среднего ±0.0091, то есть ничего. Три последние
точки неразличимы.

**Но у драфт-модели полка НЕ достигнута:** её AUC растёт всю дорогу,
0.5506 → 0.5935, на последнем шаге +0.0081. Это ровно та модель, на которой
держатся первые пятнадцать минут с половиной всей ошибки. Значит качать
матчи стоит — но ради драфта, а не ради стейт-модели, и мерить результат
надо AUC драфта, а не общим log loss.

Если качаете:

```powershell
python -m dwp.collect --n 3000        # возобновляемо, можно прерывать
python -m dwp.check_schema            # ОБЯЗАТЕЛЬНО до обучения
```

**Осторожно с двумя вещами.** Первое: `check_schema` на реальных данных
никогда не выполнялся, и вывод про `team = victim` подтверждён только против
собственного генератора — это главный кандидат на расхождение. Второе: мета
меняется патчами, и старые матчи не эквивалентны новым. После кривой обучения
это перестало быть оговоркой и стало главным доводом: **раз объём исчерпан,
единственное, что ещё может дать добор данных, — это их свежесть.**

**Методическая оговорка, которую стоит запомнить отдельно от чисел.** Замер
урезает ТОЛЬКО обучающий пул: тест внутри сида не меняется, иначе разница
между точками мерила бы заодно и уменьшение теста. И отброшенные матчи
выбрасываются из истории Elo тоже — Elo это признак, и оставить в нём исходы
«невиденных» матчей значило бы протечку, которая занижает эффект объёма.
Оба решения стоят одной строки кода и меняют вывод.

## Шаг 5. Свободное золото командой

**Зачем.** Единственная величина из блока сборок, которая в лайве точна
(`Σ players[].gold`), а в модели её нет вовсе. В концовке это прямая мера
«сможет ли команда выкупиться» — то есть ровно та часть буйбэков, которую
лайв всё-таки видит, и та самая, из-за которой расходится `gold_adv`.

На истории она восстанавливается как «добытое минус потраченное» с медианой
ошибки около 900 золота на игрока (уже проверено, `dwp.builds`). Это в разы
точнее, чем восстановление всего нетворса.

**Как проверить.** Добавить одним столбцом в `export --what extras` и
прогнать `dwp.bench_extras` на нескольких сидах. Критерий тот же: интервал
не должен накрывать ноль, и знак должен держаться на всех сидах.

## Чего делать не нужно

Всё это уже измерено и отклонено. Каждый пункт выглядит естественной идеей и
будет предложен снова — поэтому он записан с числом.

| идея | замер | вывод |
|---|---|---|
| больше матчей для стейт-модели | полка с ~3200; шаг 4202→5253 дал −0.0005 при ±0.0091 | объём исчерпан, резерв в свежести и в драфте |
| разнородный ансамбль (разные гиперпараметры) | −0.0005, 95% [−0.0017, +0.0006] | +60% инференса за неотличимое от нуля |

| «если темп сохранится» на экране | ошибка 0.1879 против 0.1796 у наивного; log loss 0.5542 против 0.5236 | проекция хуже, чем ничего не делать |

## Шаг 6. Тридцать матчей ОДНОЙ моделью

**Зачем.** Это единственное число проекта, которое меряет то, что реально
видел зритель, — и единственное, которое пока не назвать. В логе 13 матчей с
добранным исходом, но записаны они четырьмя разными моделями (`base_b`,
`exact_b`, `live`, `live_exact`). Считать их одной кучей нельзя: получится
среднее по четырём разным кривым, а `livecheck` честно разносит их по
моделям — и тогда у каждой остаётся по три-восемь матчей, чего мало.

**Что делать.** Просто смотреть матчи панелью: умолчание теперь ансамбль,
значит новые записи пойдут под одним именем `ens_03+…+ens_13.pkl`. Досматривать
до конца — оборванный на 20-й минуте матч даёт строки без поздней части, а
она самая шаткая (обещанный ECE после 50-й минуты 0.075 против 0.021 до 40-й).

```powershell
python -m dwp.web                 # смотреть, панель пишет сама
python -m dwp.livecheck           # добрать исходы и посчитать
```

**Критерий приёмки:** тридцать матчей с обоими исходами под одной моделью.
Тогда ECE лайва станет величиной, а не диапазоном между 0.126 и 0.034.

**Чего ждать.** Скорее всего ECE окажется хуже офлайнового: офлайн мерен на
выгрузке OpenDota, а в лайве к этому добавляется расхождение `gold_adv`
(до 22 п.п. в концовке с буйбэками). Ансамбль часть этого должен снять —
на холдауте он опустил ECE с 0.0155–0.0315 до 0.0082.

## Гигиена: что прогонять после любой правки

```powershell
python -m dwp.test_live_replay --n 40 --model models\ens_*.pkl
python -m dwp.test_live_fixture
python -m dwp.test_collect_fake
python -m dwp.test_map_geometry

python -m dwp.test_forecast
python -m dwp.test_web_snapshot
python -m dwp.livecheck --offline
python -m dwp.live --once --from-file data\live_dump_late.json --map
python -m dwp.holdout
```

То же одной кнопкой: панель, раздел «данные и обучение» → «Прогнать все
проверки».

Все должны дать код 0. Главные два:

- **`test_live_replay`** сверяет лайв-путь с офлайн-путём построчно и ловит
  расхождения, которых не видно по метрикам;
- **`test_web_snapshot`** гоняет настоящий матч через `Poller.snapshot` —
  то есть через тот же код, что работает в браузере, — и проверяет заодно,
  что число на панели совпадает с числом консольного пути до 1e-9. Панель
  собирает вокруг числа ещё шесть блоков, и уронить её может любой из них,
  ничего не сделав с самим числом.

`test_builds` держит точность восстановления инвентаря и границы таблицы
шансов, `test_killfeed` — то, что лента не выдумывает пар, `test_forecast` —
что коридор молчит там, где данных нет, и не переворачивает стороны.

И одно правило, которое дороже всех тестов: **инвариант, проверенный только
на фикстурах, которые вы сами и придумали, не проверен.** Так был пропущен
молчаливый ноль по зданиям, стоивший 62 п.п. на экране, — его нашёл
реплей-стенд на настоящих матчах, а не рассуждение.
